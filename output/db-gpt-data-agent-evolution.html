DB-GPT：从 ChatBot 到 Data Agent 的架构演进

每一步都在补一块缺口 · 依据本地分支与 docs/design 设计文档整理（2026-11）
① 演进脉络：5 个阶段，从"能对话"到"能交付一份可核对的分析"
早期
固定场景 ChatBot
NL → 单点
  • ChatDB：自然语言查库
  • ChatExcel：表格问答
  • ChatKnowledge：文档问答
  • 核心链路：识别表 → 生成 SQL → 执行
缺口：任务被切在固定场景里，跨库/跨文档/跨计算的复杂问题无处承载
V0.5 – V0.6
工作流与应用期
AI 原生数据应用
  • AWEL：DAG 工作流编排
  • 应用构建 / 编排 / 分发
  • 检索与可视化增强
  • SystemApp 组件生命周期
缺口：步骤明确的流程可写死，但工具生态封闭，失败与产物无统一治理
V0.7
工具开放期
生态与模块化
  • MCP / Skill 协议接入外部工具
  • 6 大 package 模块拆分
  • 配置体系重做
  • 多 LLM Provider 抽象
缺口：工具能接了，但任务仍是单轮，缺自主推进、沙箱与产物沉淀
V0.8
自主任务期
Agent 自主分析
  • 自主规划：读 schema → 多步查询 → 计算
  • Skills：可复用工作方法
  • SQL / Python 沙箱隔离执行
  • 报告交付 + 过程回看
缺口：口径、粒度、血缘、对比窗口全靠模型自由发挥，数字对不上业务预期
当前（2026）
领域化 Data Agent
可核对 · 可治理 · 可复用
  • 六层语义层：元数据/含义/指标版本/join 图/样例/规则
  • 专家套件：取数 / 分析 / 元数据 / SQL 优化 / MySQL 运维
  • Harness 运行时（DB-GPT 引擎 / pi 引擎适配）
  • 审批中心 + 可追溯报告 + 反馈飞轮
目标：把"SQL 能跑"推进到"结果可核对、口径可溯源、经验可沉淀"
② 区别于通用 Agent：DB-GPT 在 Data 领域做了哪些层的优化
维度
通用 Agent（ReAct + 通用工具）
DB-GPT Data Agent（领域层增强）
知识
来源
通用 RAG：文档切片 + 向量召回；模型自由理解字段含义
六层语义栈：物理元数据 → 业务含义 → 指标 + 口径版本 → join 路径图 → verified 样例 → 规则护栏；结构化库为权威源，向量只是索引
口径
管理
无口径概念；"销售额"按下单还是付款、是否含退款，靠模型猜
指标 = 身份，口径 = 版本载荷：表达式 + 默认过滤 + 时间粒度 + 去重规则；草稿 → 人审 → 发布；历史会话 pin 版本可复现
工具
调用
工具集全开放，模型自主选；无白名单、无成本预估
按场景绑工具白名单：取数=只读 SQL + 导出；分析=加图表/报告；运维=EXPLAIN/慢日志/DDL 受控；大扫描、DDL 走审批 dock
执行
环境
直接在宿主环境跑代码/查询，无隔离
沙箱隔离（Python/SQL 双沙箱）；只读/读写分级；从库路由；行数上限与超时由 sem_rule 强制
工作
方法
靠 system prompt 临时约束，每次任务从零摸索
专家套件 = 可安装能力包：SOP（如分析 playbook）+ 参考知识 + 工具边界 + 产物契约；套件可升级、可审计、可跨会话复用
产物
交付
文本 / 代码片段；数字从哪来、SQL 是什么，靠用户自己翻
可追溯报告：trace_id 串联五类日志；每个数字点开看 SQL 与结果；每个图表看数据/单位；产物依赖、引用来源、修订记录全留痕
反馈
进化
对话记忆，下次未必复用
反馈飞轮：👍 → verified 样例进 few-shot 库；✏️ → 语义草稿进人审队列；表结构漂移 → 关联指标自动标 stale 进复审
治理
审计
无统一审计；高危操作无 gate
审批中心（待办队列 / 策略 / 白名单）+ 五类日志审计 + 发布日志（谁在何时改了哪个口径版本）
通用 Agent：能力通用，领域知识与治理靠外挂 DB-GPT Data Agent：把口径、工具、执行、产物、反馈都做成领域原语
③ 不止取数/分析：相比 ChatDB 薄壳，DB-GPT 在 DB 领域本身做了什么
环节
ChatDB 类产品（薄壳）
DB-GPT 领域纵深
对"连接"的理解
连接 = 一个 SQLAlchemy engine；问的时候才 introspect 一次，schema 直接塞进 prompt
连接 = 元数据同步管道的起点：introspect → sem_table/sem_column（类型/约束/索引/分区/基数/采样）→ 视图与存储过程定义入库（代码态口径源）→ freq_score 表热度 → 漂移检测（列删/改/类型变 → 关联指标自动标 stale）
对 schema 的态度
schema 只是"能写进 SQL 的字段清单"，不关心库设计本身合不合理
元数据与架构专家：/data-dictionary 物理字典（真实目录查询 CSV）、/physical-er ER 图（真实 FK 实线、推断关系虚线，可下载 drawio/DBML/Mermaid/SVG）、/schema-doc HTML 结构文档、/model-review 建模评审与迁移验证清单
对 SQL 的态度
只追求"SQL 能跑"；生成完就结束，不解释执行计划
SQL 优化专家：/sql-diagnose EXPLAIN 解读 + 执行计划证据 + HTML 报告；/sql-rewrite 改写 diff + 语义等价验证清单；/index-advise 索引候选 DDL + 已有索引对比 + 实测方案；/sql-review 变更风险 + 上线验证与回退清单
对 DBA 日常
完全不碰；数据库运维是 DBA 的事
MySQL 运维专家 7 技能：SQL 体检（24 项索引失效原因 I-01~I-24 可追溯、扫描放大比为锚点）/ 实例巡检（8 域判读、两次采样算速率、参数漂移矩阵）/ 故障应急（T1–T10 决策树、先保现场再止血、每个动作带回退命令）/ 变更评审（INSTANT/INPLACE/COPY 判定、9 条一票否决）/ 备份恢复（RPO/RTO 实测、6 种误删找回代价排序）/ 参数调优（内存总账一票否决、明确"不建议改的清单"）/ 运维报告（容量触顶日期、上期承诺闭环）
零配置可用
必须先接库才能用；接不到就没东西可查
贴输出就能用：先贴 EXPLAIN / SHOW STATUS / SHOW ENGINE INNODB STATUS / 慢日志 / 监控导出 → 出结构化结论；连接器是"增强"不是"必需"，连上才减少人工搬运
工具与执行边界
一个 db_query 工具，任意 SQL 都能跑；无白名单、无审批、无分级
场景工具白名单 + 审批 dock + 沙箱：取数=只读、分析=只读为主、运维=DDL 受控；大扫描/DDL/生产变更走审批；sem_rule 强制只读/租户注入/软删除/行数上限/从库路由；命令 L0–L3 风险分级 + 六条硬红线（不猜数据、不默认改参数、主库不做重活、无备份不做恢复、不删文件、输出脱敏）
一句话定位
数据库 = 被动查询后端；能力 = NL → SQL → 表格
数据库 = 被持续观察与治理的对象；能力 = 取数 + 分析 + 元数据 + SQL 优化 + 运维 + 变更治理，全程留痕、可回退、可沉淀
④ 企业部署：数据库在云端（阿里云 / 字节云），怎么连才安全
✗ 不要这么做
DB-GPT 公网部署 → RDS 开公网地址 → 用高权限账号 → 模型自主跑任意 SQL
DB-GPT（公网） │ 任意 SQL / 任意账号 ▼ 云数据库（公网地址） · 3306 暴露在公网 · 高权限账号 · 无审批、无审计
风险：SQL 注入、全表扫描打爆生产、误删表、凭据泄露后无法追溯
✓ 推荐这么做
同 VPC 私网部署 → 连只读从库 → 最小权限账号 → 审批 + 沙箱 + 规则三重 gate
企业 VPC DB-GPT（ECS/ACK） · 审批中心 ApprovalCenter · 语义层 sem_rule · 沙箱 + 工具白名单 · 五类日志审计 │ 私网:3306（安全组白名单） ▼ 只读从库 / 分析库 · 独立只读账号 · 限 schema/table · 行数上限 + 超时 生产主库 ← DBA 人工 / 变更工单 · 模型不直接连 · DDL/参数走审批
原则：LLM 不碰生产主库；变更永远人工；凭据最小化
DB-GPT 内置的 5 道连接防护（需要企业自己开启，不是默认全开）
防护层 机制 来源
网络层同 VPC 私网 + 安全组白名单；公网入口走网关鉴权部署侧配置
账号层独立只读账号，权限精确到 schema/table；不授 DDL/GRANTDBA 建账号时定
规则层 L6readonly 拦 DDL / limit 行数上限 / replica 强制从库 / tenant_filter 多租户 / soft_delete 过滤语义中心 sem_rule
审批层高危操作 auto/confirm/deny 三档；大扫描、DDL、生产变更弹确认卡ApprovalCenter 设计
执行层场景工具白名单；Python/SQL 双沙箱；命令 L0–L3 分级；六条硬红线专家套件 + Harness
落地建议：初期可以不直接连生产库，让 DBA 把 EXPLAIN / SHOW STATUS / 慢日志输出贴进来，模型先出诊断结论；信任建立后再开放只读从库。生产 DDL / 参数调整 / 数据订正永远走人工，不通过模型自动执行。
