# 专家套件智能创建：技术衔接建议

本文件是待评审的技术建议，配套 `design.html`。没有修改业务代码或安装套件。接口、事件与新增对象均为建议名称，不代表已实现。

## 已验证的基础

| 现有能力 | 仓库依据 | 衔接方式 |
| --- | --- | --- |
| 千问原生包与旧格式包解析、文件摘要、技能摘要 | `packages/dbgpt-serve/src/dbgpt_serve/plugins/loader.py` | 生成器输出原生包，最终使用同一解析器投影现有套件快照 |
| ZIP 上传、路径与解压大小检查、文件树替换及异常恢复 | `packages/dbgpt-serve/src/dbgpt_serve/plugins/api/endpoints.py` 的 `upload_suite` | 抽取公共安装服务，供上传和产物安装调用；不在前端模拟上传 |
| 安装、启停、审计、会话绑定记录 | `plugins/service/service.py`、`plugins/registry.py` | 保留现有注册表与调用协议 |
| 套件页、上传与详情 | `web/pages/construct/suites/index.tsx` | 增加智能创建入口，保留文件导入 |
| 列表、详情、启停、卸载客户端 | `web/client/api/suite/index.ts` | 增加草稿、校验和产物安装客户端 |
| 运维流程与实际套件资产 | `assets/suites/db-ops/.qwenwork-plugin/plugin.json`、`prompts/`、`skills/` | 作为创建模板和结构参考，不重复建设一个平行的 DB 运维套件系统 |
| 运行时套件绑定 | `packages/dbgpt-app/src/dbgpt_app/openapi/api_v1/suite_binder.py` | 完整安装后复用现有绑定入口；生成草稿不能被绑定 |

当前上传接受 `.zip`，压缩包与声明的解压内容上限均为 50 MiB。上传会按套件名称替换目标文件树，并调用注册服务；它不是面向对话产物的受控安装接口。现有 loader 是宽松、失败降级的加载器，部分缺失内容只产生警告。因此“能被加载”不能直接当作“生成质量校验通过”。

当前前端的市场数据为空。创建闭环不依赖市场接入。

## 三个对象要分开

1. **SuiteDraft**：创建任务及可编辑草稿。关联创建会话、操作者、材料、需求摘要、生成文件和修订号。存放在隔离草稿目录，不能被启动扫描或可执行套件目录扫描到。
2. **SuiteArtifact**：冻结某个修订的完整 ZIP、文件清单、校验报告和包内容摘要。产物一经生成不可变；修改创建新产物。校验针对这一具体内容，不能复用旧结果。
3. **SuiteInstallation**：某个产物在目标范围的安装结果。沿用现有注册实体；补充产物关联及由可靠身份得到的操作者记录。安装结果与草稿状态分别保存。

不要把一个尚未安装的草稿直接插入 enabled 注册表，也不要把套件包简单当作普通 ZIP 下载链接。

## 创建器与运行器分工

创建入口在对话中附加“专家套件创建”上下文，加载创建技能与编排规则。创建器负责读材料、组织能力、写文件和调用校验；安装由用户点击产物卡片触发。

创建器可以作为内置技能 / 能力实现，不必把创建器本身作为一个默认选中的业务专家套件。明确区分 `creation_mode` 与目标产物 `suite_name`，避免套件绑定器把创建过程绑定成业务套件执行。

DBGPT 与 PI 共享相同的草稿工具、校验服务和产物契约，各自仅做工具调用和流式适配。工具名建议：

- `suite_draft_create`：建立草稿，返回草稿 ID。
- `suite_draft_write`：仅写当前草稿的受控相对路径，支持生成或修改内容。
- `suite_draft_read`：查看草稿及文件正文。
- `suite_draft_validate`：返回错误、警告及资源需求。
- `suite_package_build`：冻结当前修订，生成完整包和 SuiteArtifact。

安装操作建议以应用 API 暴露给卡片，而非向创建模型提供可以任意写入正式套件目录的 shell 权限。通用文件写入不能绕过草稿隔离和安装检查。

## 包格式

P0 推荐输出当前已经支持的 `.qwenwork-plugin/plugin.json` 原生格式；继续兼容旧 `suite.yaml` 导入，但生成时只维护一份主清单，避免两份描述发生漂移。

```text
<suite-slug>/
  .qwenwork-plugin/plugin.json
  README.md
  prompts/workflow.md
  skills/<skill-slug>/SKILL.md
  skills/<skill-slug>/references/*.md
  references/*.md
```

清单沿用当前原生包字段及 `dbgpt` 扩展，覆盖：

- 名称、版本、描述、作者、技能目录。
- 工作流程、指令到技能的引用、推荐问题。
- 工具允许/禁止声明、需要的资源、审批约束。
- 输出种类与完成条件。

校验报告、生成来源和依赖解析结果可以保存在产物侧的伴随元数据中；如需写入包，要定义明确版本化的扩展，不能假设当前 loader 会保留未知字段。

需要一个 **依赖解析步骤**：从技能声明定位当前引擎真正注册的工具及输出渲染能力，形成确定的依赖清单。不要只靠技能正文中“可以调用 XXX”的自然语言就认定它可运行，也不能把模板里的抽象工具名称等同于两种引擎当前实际的工具 ID。

P0 复用已有工具与已接入连接器，不自动生成和启用任意新的可执行扩展。需要新增工具的需求应明确标为后续扩展，不伪装成可运行能力。

## 校验必须区分层次

### 1. 包结构与完整性

检查主清单必需字段、包内路径、完整技能正文、指令目标、工作流程/参考文件的可解析引用、重复名称、工具声明与注册映射、输出契约。

生成包的质量校验采用严格模式：阻断项不能被当前宽松 loader 的 warning 忽略。除普通导入防护外，核对解压实际字节、重复 ZIP 路径、文件数量及所有读写引用边界，避免包内文件读到草稿根之外。

### 2. 安装兼容性

对目标范围核对引擎、工具、渲染能力和操作者安装权限。对数据库、连接器等资源区分：

- **平台必要能力缺失**：包的必要工具无法在目标系统解析，阻断安装。
- **用户必要配置缺失**：包结构完整，可以安装但保持 disabled；配置后 enable。
- **可选配置缺失**：可以安装，明确说明受影响能力。

资源凭证不进入套件包，实际资源访问使用运行时权限。套件声明只能进一步限制现有权限，不得提升授权。

### 3. 真实任务试跑

另一个明确操作；需要用户选择资源，记录真实工具轨迹、输出与引用，不用结构校验结果冒充试跑结果。P0 可以只提供“尚未试跑”说明；若开放试跑，运行时遵守现有只读及审批规则。

## 对话产物协议与 UI

建议在通用产物契约中加入 `artifact_type = expert_suite`，而不是只根据 `.zip` 后缀识别。

```json
{
  "artifact_type": "expert_suite",
  "artifact_id": "<不可变产物ID>",
  "draft_id": "<草稿ID>",
  "revision": "<对应修订>",
  "suite_name": "<slug>",
  "display": "<名称>",
  "version": "<包版本>",
  "package_digest": "<规范化包内容摘要>",
  "validation_status": "ready",
  "dependencies": [],
  "preview_ref": "<应用内预览引用>",
  "download_ref": "<应用内下载引用>"
}
```

这是契约示意，字段值均为占位，不是生成的实际产物。

- 进度复用已有 `assistant.progress`；文件工具调用复用时间线并显示读取/写入正文。
- 可新增 `suite.draft.updated`、`suite.validation.updated`，最终 SuiteArtifact 使用统一产物事件传递。
- 卡片进入通用 ArtifactCards / ArtifactRail；预览复用右侧产物区域，提供文件与技能正文。
- 实时事件与存储历史共用一种规范数据结构，刷新后按 artifact ID 恢复。
- 安装状态通过产物 ID + 目标范围查询真实注册结果，不由 LLM 文本决定。
- 文件名和模型输出作为普通文本显示；HTML / Markdown 预览沿用安全渲染流程。

## API 建议

以下是新增建议；实现时遵守现有 Result 返回协议及路由约定。

| 操作 | 建议接口 | 关键约束 |
| --- | --- | --- |
| 草稿建立 / 查询 | `POST /api/v1/suite-drafts`、`GET /api/v1/suite-drafts/{id}` | 使用可靠身份；只访问授权草稿 |
| 修改草稿 | `PATCH /api/v1/suite-drafts/{id}` | 携带预期修订，拒绝并发覆盖 |
| 校验 / 打包 | `POST /api/v1/suite-drafts/{id}/validate`、`POST /api/v1/suite-drafts/{id}/build` | 校验与构建冻结同一修订；生成不可变 artifact |
| 预览 / 下载 | `GET /api/v1/suite-artifacts/{id}`、`GET /api/v1/suite-artifacts/{id}/download` | 应用管理路径，不接受任意本地绝对路径 |
| 一键安装 | `POST /api/v1/suite-artifacts/{id}/install` | 预期摘要、目标范围及幂等键；身份来自服务端认证 |
| 安装结果 | `GET /api/v1/suite-artifacts/{id}/installation` | 真实结果用于刷新和多页面同步 |

静态 `upload` 路由与 `/{name}` 等动态路由共存时要避免路由遮蔽；新增 API 独立命名空间能减少与现有套件名称冲突。

不能把客户端传入的 `user_name` 当成安装授权依据。当前接口的身份/范围能力仍需要梳理，实例安装与个人/团队安装不能只靠前端切换文案实现。

## 安装事务

1. 固定 artifact 内容，核对摘要和严格校验结果。
2. 校验目标范围权限、兼容性及同名冲突。
3. 为目标身份获取安装锁；相同内容的重复请求返回已有结果，不重复写注册记录。
4. 使用公共安装服务处理 staging 文件与注册事务，不复制一份与上传不同的解压实现。
5. 安装后重新解析实际文件，用实际内容生成快照；必要资源缺失时注册 disabled。
6. 保存产物关联及安装审计，返回真实 SuiteResponse。
7. 成功后刷新前端套件缓存、选择器和产物卡片。

失败恢复需要覆盖文件移动与注册事务，不只恢复目录。任何一步失败均不能把无效新文件和 enabled 快照暴露给运行器。安装完成但客户端断线时，重试必须读到成功结果。

P0 同名不同内容一律改名另存，阻断当前上传的静默替换逻辑用于此入口。安装官方名称的副本也使用新身份。上传升级是现有能力，但不能因此宣称已经有多版本回滚。

P1 升级前，要把存储扩展为不可变的版本内容，保证已有会话绑定的旧版本文件可读取。仅保存版本号或 pin 审计不够：覆盖同一个目录后，旧版本文件不会自动保留。

## 建议的落点与验证

前端：套件页增加创建入口；首页创建上下文与业务套件绑定分离；通用产物卡片增加 expert_suite 分支；预览新增技能和文件视图；安装后失效套件列表缓存。新套件从选择器发现，保持首页初始不选中。

后端：在 plugins 服务旁新增草稿/产物服务；从上传接口抽取公共安装器；为 loader 增加明确的生成产物严格校验层；把创建工具接入 DBGPT 与 PI 的工具适配。

验证应以真实行为为主：

- 两引擎都得到同一产物类型、文件预览与真实校验状态。
- 缺技能、错误指令引用、未知工具、非法路径阻断安装。
- 修改后的校验绑定新摘要；并发编辑不覆盖，旧卡片不误装新内容。
- 重复点击和网络重试只安装一次；冲突不覆盖官方/原有套件。
- 安装失败恢复完整；资源待配置套件不进入 enabled 选择器。
- 安装后可从新业务对话加载技能正文；刷新创建对话仍能查看产物和真实安装状态。

本设计只完成产品与技术方案，不对当前模型生成质量、实际工具依赖完备程度或多用户权限隔离作未经验证的保证。
