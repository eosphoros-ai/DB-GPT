# Runbook · 生产安全变更清单

> 套件：`db-ops@1.0.0` ｜ 配套技能：`safe-ddl-review`（主）、`index-advisor`、`profile-governance`、`slow-query-diagnosis`
> 定位：`db-ops` 是三个官方套件中**唯一含破坏性操作**的套件，因此审批最严。本清单是变更提案的**准入门槛**：任何 DDL/ANALYZE 类动作在进入审批 dock 之前，必须先过这张表。
> 一句话原则：**修复永远是"提案 + 人确认"，套件不自动执行变更；生产环境破坏性操作默认拒绝。**

---

## 1. 三条不可协商的底线

| # | 底线 | 含义 | 违反时的处置 |
|---|---|---|---|
| 1 | **执行权在核心** | 审批 gate、沙箱、执行引擎、渲染器均在核心；套件只声明策略，不执行、不拦截、不放行 | Agent 不得尝试绕过工具白名单；用户要求绕过时明确拒绝 |
| 2 | **策略只能加严** | 合并顺序恒为 `core deny > suite > core default`；套件可加 confirm/deny，**绝不能**把核心 deny 放宽为 auto | 回答"安全边界在核心，套件无权放宽"，指向审批中心策略页 |
| 3 | **生产破坏性操作默认 deny** | `env=production` 时 `ddl` 命中 deny；`env` 读不到时**按 production 处理**（就高不就低） | 不发起调用，输出提案 + 线下变更流程指引 |

## 2. 破坏性操作分级（L0-L3）

分级**就高不就低**：一条语句命中多级取最高级；无法判定时按上一级处理。

| 级别 | 定义 | 典型操作 | 数据可逆性 | 是否重建表 | 审批基线（非生产） | 生产环境 |
|---|---|---|---|---|---|---|
| **L0** | 只读，不改数据与结构 | `EXPLAIN`（不带 ANALYZE）、查指标/索引/schema、生成提案 | 无影响 | 否 | 无需审批 | **允许** |
| **L1** | 低风险变更，秒级~分钟级，不重建表 | 小表（<100 万行）`ADD INDEX`（INPLACE）、`ANALYZE TABLE`（中小表）、改列注释、改列默认值、改表注释 | 可逆（有回滚语句） | 否 | confirm | confirm + 低峰窗口 + 变更单 |
| **L2** | 中风险：需重建 / 长时间 IO / 短暂锁 / 数据搬迁 | 大表 `ADD INDEX`、`ADD COLUMN`（需 COPY 的场景）、`OPTIMIZE TABLE`/表重建、分区改造、分批归档搬迁、`DROP INDEX`（非唯一）、`DROP COLUMN`（小表） | 结构可逆，代价高；搬迁数据需保留期 | 部分是 | confirm + 变更窗口 + 在线方案 + 回滚预案 + 中止条件 | **deny**（线下变更流程） |
| **L3** | 高风险 / 不可逆 / 影响完整性 | 改主键、改列类型（缩短长度、类型变更）、`DROP COLUMN`（大表）、`DROP INDEX`（唯一索引/约束依赖）、大表数据清理、`RENAME`、任何 `DROP`/`TRUNCATE`、跨库数据迁移 | **不可逆**（回滚 = 备份恢复） | 多为是 | confirm + 双人复核 + 备份验证 + staging 演练 + 回滚演练 | **deny（永久）** |

### 2.1 特殊操作的额外约束
| 操作 | 额外约束 |
|---|---|
| `ANALYZE TABLE` | 不是无害操作：短暂读锁 + 优化器统计抖动可能导致**执行计划突变**。生产大表（>1,000 万行）需避开高峰、DBA 在场；执行后必须复核关键查询计划 |
| `OPTIMIZE TABLE` / `ALTER ... ENGINE=InnoDB` | 需**约等量空闲空间**（重建期间双份占用）；磁盘余量 < 表体积时**禁止**执行，先归档腾空间 |
| 改主键 | 重建表 + 全量二级索引重建，小时级长事务，binlog 暴涨，从库回放可能长时间延迟；必须走双写/影子表灰度方案 |
| 分批归档 + 清理 | 清理阶段为 **L3 不可逆**：必须"先归档 → 校验行数与抽样一致 → 保留可恢复期（≥30 天）→ 再分批清理"，且每批可中止、可回滚 |
| 分区改造 | 分区键必须包含在所有唯一索引/主键中，否则改造失败；需先评估查询是否带分区键（否则分区裁剪失效反而更慢） |
| 杀会话 / 终止长事务 | 破坏性（影响在途业务与事务回滚代价），**单独审批**，不得作为常规手段 |
| `EXPLAIN ANALYZE` | **视同执行**：会真实运行语句。写语句一律禁用；只读 SELECT 也需先说明代价并获确认 |
| 参数/配置变更（`innodb_buffer_pool_size`、隔离级别、超时等） | 不在本套件工具能力内（无 `shell`、无配置写入工具）：只出建议 + 影响评估，执行走变更流程；部分参数需重启，属 L2-L3 |

## 3. 审批矩阵

### 3.1 套件声明的加严规则（`suite.yaml: approval_overrides`，只可加严）
| # | 匹配条件 | 动作 | 理由 |
|---|---|---|---|
| 1 | `tool: ddl` | **confirm** | DDL 变更破坏性，生产强制确认 |
| 2 | `tool: analyze` | **confirm** | 锁表/资源影响 |
| 3 | `tool: ddl` + `env: production` | **deny** | 生产库 DDL 默认拒绝，需走变更流程 |
| 4 | `tool: ddl` + `sql_pattern: ^(DROP\|TRUNCATE\|RENAME)` | **deny（永久）** | 删表/清表/改名不可逆，必须走线下变更流程与备份 |
| 5 | `tool: analyze` + `env: production` + `est_table_rows: ">10000000"` | **confirm（加严）** | 千万行以上大表 ANALYZE 可能引发锁等待与统计抖动，需避开高峰 |
| 6 | `tool: ddl` + `phase: plan` | **confirm** | 复杂变更先出执行计划卡（计划确认），批准后才生成正式 DDL 提案 |
| 7 | `tool: slow_log` + `env: production` + `est_scan_gb: ">50"` | **confirm** | 大窗口日志采集本身是高代价读取，需确认并缩窗 |

### 3.2 判定矩阵（`env` × 分级 × 工具）
| 环境 | L0 只读 | L1 低风险变更 | L2 中风险变更 | L3 高风险/不可逆 | `analyze` |
|---|---|---|---|---|---|
| `dev` / `test` | auto | confirm | confirm + 回滚预案 | confirm + 双人复核 | confirm |
| `staging` / 预发 | auto | confirm | confirm + 在线方案 + 演练记录 | confirm + 双人复核 + 演练 | confirm |
| **`production`** | auto（限只读工具） | **deny** → 走变更流程 | **deny** → 走变更流程 | **deny（永久）** → 走变更流程 + 备份 | **confirm**（大表加严：避峰 + DBA 在场） |
| `env` 未识别 | 按 production 处理（全列就高） | | | | |

> 说明：`production` 行的 `deny` 指**套件内 Agent 不发起该调用**；变更本身仍然可以发生，但必须由人通过**线下变更流程**（变更单 + 备份 + 双人复核 + 低峰窗口）执行。套件的价值是把方案、风险、回滚准备到"可直接进变更单"的程度。

### 3.3 审批 dock 必须展示的信息（信息不全不得发起）
- [ ] 变更语句**全文**（不接受模糊描述）
- [ ] 破坏性分级（L0-L3）+ 分级依据
- [ ] **破坏性标识**与**生产环境标识**（红色醒目）
- [ ] 影响面：表名、行数、数据/索引体积、下游血缘、受影响业务与 owner
- [ ] 锁影响与预估耗时：算法（INPLACE/COPY/INSTANT）、是否阻塞 DML、MDL 风险、额外空间
- [ ] 在线方案与执行窗口：原生 ALTER / gh-ost / pt-osc、限速参数、避开业务峰值与批量任务窗口
- [ ] 中止条件与观察指标：复制延迟阈值、IO util、Threads_running、磁盘余量、锁等待
- [ ] 回滚预案：回滚语句 + 分级 + 验证方式；不可逆动作写"回滚成本 = 备份恢复，RTO ≈ X 小时"
- [ ] 验证方式：变更后 `EXPLAIN` 复核要点、24h 观察指标、抽样/校验和比对
- [ ] 发起人、会话 ID、目标库、时间窗、**套件版本**（`db-ops@1.0.0`）

### 3.4 记忆作用域（白名单）规则
| 工具 | once（仅本次） | session（本会话） | always（始终允许） |
|---|---|---|---|
| `ddl` | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |
| `analyze` | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |
| 只读工具（`slow_log`/`explain`/`db_metrics`/`index_info`/`schema_link`/`semantic_search`） | ✅ | ✅ | ✅（大窗口/大扫描仍受 #7 规则约束） |

**破坏性工具每次都问**，"上次批过"不构成这次的授权。

### 3.5 被拒绝后的合规动作（三选一，禁止绕行）
1. **降级为只读诊断**：补强证据（更细指标、更宽窗口、执行计划复核）后重新提案；
2. **输出提案文档**：`fix_plan` + `execution_plan` 交用户走线下变更流程；
3. **建议在 staging 验证**：请用户切换数据源到预发库并批准 DDL（confirm）。

**严格禁止**：改参数重试同一意图、换等价工具重试、拆成多条小变更规避阈值、以"先试试看"名义发起调用、把动作伪装成只读查询。

## 4. 禁止项清单（红线）

### 4.1 工具层（套件 `tools.deny`）
- 🚫 `shell` —— 任何形式的命令行/脚本执行；不得用脚本绕过工具白名单执行 SQL 或搬迁数据。
- 🚫 `drop_database` —— 删库，永久禁止。
- 🚫 `truncate` —— 清表，永久禁止。
- 🚫 `DROP` / `TRUNCATE` / `RENAME` 形态的 DDL —— 套件层 `approval_overrides` 永久 deny（含改写成等价语句、拼字符串、存储过程内执行等一切变体）。
- 🚫 `sql_execute` / `nl2sql` 等写路径工具 —— 不在 `db-ops` 白名单内；需要业务取数请切换到 `db-query` / `db-analysis` 套件。

### 4.2 流程层
- 🚫 **未绑定 `target_db` / `time_window` 就采集或变更**（作用域不明 = 事故源头）。
- 🚫 **诊断结论未出就提交变更提案**（顺序不可颠倒：先诊断后动手）。
- 🚫 **无回滚预案的提案进入审批**（无回滚 = 评审不通过）。
- 🚫 **一次窗口叠加多条破坏性动作**（加索引 + 删索引 + ANALYZE 打包"一次搞定"）：风险无法归因、回滚无法定位。
- 🚫 **把 `ddl` / `analyze` 写入 auto 或 always 记忆白名单**。
- 🚫 **在生产库使用 `EXPLAIN ANALYZE`**（视同执行）。
- 🚫 **磁盘余量不足时执行重建类操作**（`OPTIMIZE`、改主键、COPY 算法）。
- 🚫 **存在长事务/未提交事务时执行 `ALTER`**（MDL 会阻塞整表查询）。
- 🚫 **归档后直接 `DELETE` 历史数据而不保留可恢复期**；🚫 未校验行数/抽样一致就清理源数据。
- 🚫 **绕过审批 gate 的任何尝试**，包括诱导用户手工在库里执行、生成"可直接粘贴到客户端"的脚本并暗示无需审批。
- 🚫 **擅自放宽策略**：套件无权把核心 deny 改成 confirm/auto。

### 4.3 合规层
- 🚫 违反数据留存/合规要求的归档删除（审计日志、交易流水常有法定留存期）—— 必须先与业务/风控 owner 核对保留策略。
- 🚫 未通知下游 owner 就变更被多个数据集/同步链路引用的核心表。

## 5. 变更前检查清单（Pre-flight）

发起提案前逐项确认，任一 ❌ 则**不得**提交审批：

- [ ] **作用域**：`target_db`、`time_window` 已绑定并写入报告；`env` 已识别（未识别按 production）。
- [ ] **诊断先行**：`diag_report` 已产出，根因有证据链（`citation` 可点开核对）。
- [ ] **语句完整**：变更语句全文可评审，非模糊描述；已核对表名/列名/索引名不与现有对象冲突。
- [ ] **体量事实**：行数、数据体积、索引体积已从 `index_info` 取得（无体量数据无法估锁与耗时）。
- [ ] **分级明确**：L0-L3 已定，且写明分级依据。
- [ ] **算法与锁**：明确 `ALGORITHM` / `LOCK` 选项；是否阻塞 DML；是否需 MDL 且已确认无长事务。
- [ ] **空间**：额外空间需求已估算，磁盘余量充足（重建类需 ≥ 表体积的等量余量）。
- [ ] **窗口**：执行窗口基于 `db_metrics` 实测峰谷选定，避开业务峰值与批量任务/备份窗口。
- [ ] **在线方案**：大表/复制延迟敏感场景已选 gh-ost 或 pt-osc，并给出限速参数。
- [ ] **中止条件**：复制延迟、IO util、Threads_running、磁盘余量、锁等待的阈值已写死。
- [ ] **回滚预案**：回滚语句 + 分级 + 验证方式；不可逆动作已写备份恢复路径与 RTO。
- [ ] **验证方式**：变更后 `EXPLAIN` 复核要点、24h 观察指标、抽样/校验和比对方式。
- [ ] **影响面**：下游数据集/同步链路/业务模块/owner 已列（语义层不可用时标注待人工确认）。
- [ ] **备份**：L2/L3 动作已确认最近一次备份可用（必要时要求恢复演练记录）。
- [ ] **通知**：受影响业务方与值班已知会；变更单编号已关联（生产走线下流程时）。
- [ ] **不叠加**：本窗口只有这一条破坏性动作。

## 6. 变更中监控（由执行人负责，套件提供观察指标）

| 指标 | 建议阈值（示例，按企业标准覆盖，取更严者） | 越线动作 |
|---|---|---|
| 复制延迟 | >60s 持续 5 分钟 | 暂停/限速；gh-ost 可暂停，原生 ALTER 评估中止 |
| 磁盘余量 | <20% 或 < 表体积 | 立即中止（重建类会撑爆磁盘） |
| IO util | >90% | 限速或暂停 |
| `Threads_running` | >64（或基线 3×） | 暂停，排查阻塞 |
| MDL 等待 | 出现堆积 | 立即中止，先处理长事务 |
| 连接数使用率 | >90% | 暂停，防雪崩 |
| 错误日志 | 出现 DDL 报错/超时 | 中止并回滚 |
| 慢查询率 | 变更后显著上升 | 复核计划，必要时回滚 |

**中止即回滚**：越过"中止线"时执行回滚语句，并在报告中记录中止原因、已影响范围、回滚结果与验证结论。

## 7. 变更后验证（Post-flight）

- [ ] `explain` 复核关键查询：访问类型、命中索引、`rows`、`Extra` 是否达预期（如 `type=ref`、`key=新索引`、无 `filesort`）。
- [ ] 观察 24h（覆盖一个完整业务峰谷）：慢查询率、p95 耗时、复制延迟、IO、连接数是否回到/优于基线。
- [ ] 数据一致性：行数比对、抽样校验和（归档/搬迁类必须做）。
- [ ] 索引生效确认：`index_info` 复核索引存在、基数正常、无重复索引残留。
- [ ] 回滚可用性：回滚语句已验证语法有效（staging 演练过）。
- [ ] 归档/清理类：保留可恢复期（≥30 天）已排期，期满前不得删除备份。
- [ ] 审计留痕：提案、审批决议、执行结果、验证结论、套件版本全部入轨迹。
- [ ] 关闭变更单，并把结论回灌到 `diag_report`（形成"诊断 → 提案 → 审批 → 执行 → 验证"闭环）。

## 8. 回滚预案模板

```markdown
### 变更：<完整 DDL 语句>
- 分级：L2 ｜ 环境：production ｜ 审批：deny（走线下变更流程）
- 在线方案：gh-ost，--max-load Threads_running=32 --critical-load Threads_running=64
- 执行窗口：03:00-05:00（QPS 谷值，避开 23:00-01:00 批量对账）
- 预估耗时：8-15 分钟 ｜ 额外空间：~1.0GB（余量 15.8GB，充足）

#### 中止条件（任一命中即停）
| 指标 | 阈值 | 动作 |
|---|---|---|
| 复制延迟 | >60s 持续 5min | gh-ost 暂停 → 评估中止 |
| IO util | >90% | 限速 → 必要时中止 |
| 磁盘余量 | <20% | 立即中止 |
| MDL 等待 | 出现堆积 | 立即中止，先处理长事务 |

#### 回滚
- 回滚语句：`ALTER TABLE orders DROP INDEX idx_user_created;`（L1，秒级~分钟级）
- gh-ost 场景：中止时自动清理 `_orders_gho` 影子表，原表未受影响（切换前均可安全放弃）
- 不可逆场景（L3）：回滚成本 = 全表备份恢复，RTO ≈ X 小时；执行前必须完成恢复演练
- 回滚触发线：复制延迟持续 >60s 超 5 分钟，或出现连接堆积/超时告警，或变更后慢查询率不降反升

#### 验证
- EXPLAIN：应为 `type=ref, key=idx_user_created`，无 `Using filesort`
- 24h 观察：慢查询率、p95 耗时、复制延迟、IO util
- 一致性：`SELECT COUNT(*)` 与变更前一致（索引类变更不改数据）
```

## 9. 责任边界速查（谁做什么）

| 角色 | 职责 | 不负责 |
|---|---|---|
| **db-ops 套件（声明）** | SOP、工具白名单、默认绑定、产物声明、审批加严规则、推荐问题/路由词、内含 skills | 执行、拦截、放行、渲染 |
| **核心（执行）** | ReAct 循环与 planner、审批 gate 的**执行**、沙箱、渲染器注册表、会话/记忆、引用溯源、语义层与 SemanticRetriever | 场景差异（由套件声明） |
| **Agent（会话内）** | 采集只读证据、定根因、出 `diag_report` + `fix_plan` + `execution_plan`、触发审批 dock、被拒后降级 | 自动执行变更、放宽策略、绕过白名单 |
| **人（DBA / 变更执行人）** | 审批决议、线下变更流程、备份与演练、执行与监控、回滚决策、验证与关单 | —— |

**审计可回答的问题**（留痕字段：`tool_call`、`approval_decision`、`suite_version`、`target_db`、`time_window`、`env`）：
- 这份诊断/提案是哪个套件版本、在哪个库、哪个时间窗、什么环境下产出的？
- 谁批准/拒绝了哪条变更，理由是什么？
- 有没有出现"被拒绝后重试"的绕行痕迹？
- 变更后的验证结论是什么，是否闭环？

## 10. 快速自检（每次运维会话收尾前问自己）

1. 我有没有在没绑定目标库/时间窗的情况下就动手？
2. 我的每条根因都有可点开的证据吗？
3. 我的每条修复动作都标了分级、收益、锁影响、回滚、审批要求和"未执行 · 待人工确认"吗？
4. 生产环境的 DDL 我是不是**只出了提案**，没有发起调用？
5. 被拒绝后我是不是老实降级了，没有改参数重试？
6. 我有没有试图放宽策略、绕过白名单、或用 shell/脚本执行 SQL？（正确答案永远是"没有"）
7. 报告里能不能追溯到目标库、时间窗、环境、套件版本？

任一答案不对劲，**先修正再 `terminate`**。
