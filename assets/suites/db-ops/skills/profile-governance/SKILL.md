# 数据库画像与治理技能 (Profile & Governance)

## 必需关联知识

所有治理变更提案均遵循[受控变更评审](../safe-ddl-review/SKILL.md)。

本技能是 `db-ops`（智能运维）套件的**中长期治理**能力，视角从"这条 SQL 为什么慢"抬升到"这个库为什么越来越重、该怎么系统性瘦身"。产出 = 数据库 profile（画像）+ 治理建议路线图。与巡检的关系：巡检发现容量/膨胀类 P1 风险后移交本技能深挖。

## 技能目标

1. 建立目标库的**结构与容量画像**：谁最大、谁增长最快、谁最"脏"（无主键/大字段/高碎片）。
2. 识别五类典型治理问题：**表膨胀、碎片、无主键、大字段滥用、冷热混存**。
3. 给出**分层治理路线图**（立刻可做 / 需变更窗口 / 需架构演进），每条标收益、风险、是否需审批。
4. 量化容量趋势，回答"不治理会怎样"（触顶时间、备份窗口拉长、DDL 耗时上升）。

## 前置条件

- `target_db` 已绑定；治理画像默认看**全库结构**，但明细分析要分批（每批 ≤20 表），避免一次性拉爆元数据查询。
- `time_window` 已绑定：用于增长趋势与冷热判定（推荐 ≥7 天，容量趋势建议 30 天分段采集）。
- 优先在只读从库/备库采集；生产主库采集需限流并在报告标注。
- `env` 可读；治理动作多为结构变更，生产命中 `deny`，本技能只出提案。

## 核心工作流程

### 1. 采集容量与结构基线
调用 `db_metrics`，传参：`target_db`、`time_window`、`granularity`（7 天→`1h`，30 天→`6h`）、`metrics: [disk_usage, data_size_bytes, index_size_bytes, table_count, connections_usage, disk_io_util, replication_lag, backup_duration]`、`aggregate: [avg,p95,max]`、`compare: {baseline: "previous_period"}`。
拿结果：库级总体积、数据/索引体积比、磁盘使用率与增速、备份耗时趋势。

### 2. 采集表级明细（分批）
调用 `index_info`（表级体量与索引事实的权威来源），传参：`target_db`、`tables`（分批列表；首批取体积 Top 20）、`include: [row_count, size_bytes, columns, cardinality, unused, duplicate]`。
需要确认字段类型、主键、注释、外键等结构信息时，调用 `schema_link`（传表名或业务关键词）取结构化 schema 事实；语义层可用时补充调用 `semantic_search` 获取表的业务归属、owner、下游血缘与重要性分级。
整理成**表画像台账**：

| 字段 | 说明 | 治理信号 |
|---|---|---|
| 行数 / 数据体积 / 索引体积 | 体量三件套 | 单表 >5,000 万行或 >50GB → 分区/归档/拆分候选 |
| 数据_free 比例（碎片率） | 可回收空间 / 数据体积 | >30% 且体积 >10GB → 重建候选（`OPTIMIZE`/`ALTER ... ENGINE=InnoDB`） |
| 是否有主键 | 无主键表 | **P1 硬伤**：复制回放慢、无法安全 Online DDL、去重困难 |
| 大字段 | TEXT/BLOB/JSON 列数与平均长度 | 行溢出、缓冲池效率下降 → 拆表/外置对象存储 |
| 最长列宽 / 平均行长 | 行密度 | 平均行长 >2KB 时扫描代价显著上升 |
| 冷热分布 | 按时间列统计最近 N 天数据占比 | 90 天前数据占比 >70% → 归档/分层候选 |
| 索引数量与冗余 | 索引数、未使用、重复 | 索引数 >6 或索引/数据体积比 >0.8 → 写入放大，转 index-advisor 清理 |
| 命名与注释 | 表/列注释覆盖率、命名规范 | 注释覆盖 <50% → 可维护性治理项（P2） |

> 冷热分布与"90 天前占比"需要按时间列聚合。若工具不能直接给出，用 `explain` + `slow_log` 侧面判断查询集中访问的时间范围，并在报告中标注"冷热判定为间接推断，需业务确认"。

### 3. 五类问题识别与定级
| 问题 | 判定 | 分级 | 治理方向 | 变更风险 |
|---|---|---|---|---|
| 表膨胀 | 单表行数/体积超阈值，且持续增长 | P1 | 归档 + 分区 + 历史库拆分 | L2-L3（数据搬迁不可逆） |
| 碎片 | 碎片率 >30% 且体积 >10GB | P2 | 表重建回收空间（需等量空闲空间 + 长窗口） | L2（长时间 IO 与复制延迟） |
| 无主键 | 存在无主键表 | P1 | 补自增/业务主键；无法补则评估重建 | L2-L3（改主键 = 重建表） |
| 大字段滥用 | TEXT/BLOB/JSON 与热数据同表 | P2 | 垂直拆表或外置对象存储，库内只留指针 | L2-L3（应用改造） |
| 冷热混存 | 冷数据占比 >70% 且查询集中近期 | P1 | 冷热分层：热表 + 归档表/归档库 + 定时归档任务 | L2（需可回滚的搬迁批次） |
| 索引冗余 | 未使用/重复索引多、索引体积比高 | P2 | 转 index-advisor 出清理提案 | L1-L2 |

### 4. 容量趋势外推
用时间窗内体积/磁盘斜率线性外推：`预计 N 天后磁盘达告警线`、`M 天后达容量上限`、`按当前增速备份窗口将从 X 分钟拉长到 Y 分钟`。
外推不超过 90 天；样本点 <3 时标注"趋势不可信"。这一步是治理提案的**紧迫度依据**。

### 5. 治理路线图（分层，不堆砌）
输出三层，每条含 `动作 / 预期收益（可回收 GB、扫描量下降、备份窗口缩短）/ 风险等级 / 前置条件 / 是否需审批 / 建议窗口`：
- **A. 立刻可做（低风险，多为只读或应用侧）**：清理未使用索引（提案）、补齐注释与命名规范、应用侧限制 `SELECT *` 与大字段随主查询返回、慢 SQL 改写移交。
- **B. 需变更窗口（L2）**：历史数据归档（分批 + 可回滚）、碎片重建、补主键、大字段垂直拆表、分区改造。
- **C. 需架构演进（L3，跨团队）**：冷热分库/历史库、读写分离扩容、分库分表评估、对象存储外置。
每条 B/C 动作必须写明**分批策略**（每批行数、间隔、中止条件）与**回滚方式**；数据删除类动作（归档后清理）标为 **L3 不可逆**，必须"先归档校验 → 再删除 → 保留可恢复期"。

### 6. 产出画像与治理报告
输出 `diag_report`（profile 形态）：
1. **画像摘要**：库体积、表数量、Top5 大表、健康结论一句话；
2. **容量与趋势**：磁盘使用率、增速、触顶天数、备份窗口趋势；
3. **表画像台账**（Top N，含碎片率/主键/大字段/冷热/索引冗余标记）；
4. **问题清单**：按 P0-P2 排序，每条挂证据（`citation` 指向指标快照或表台账行）；
5. **治理路线图** A/B/C 三层；
6. **影响面**：下游数据集/同步链路/业务模块（语义层可用时）；不可用时标注待人工确认；
7. **采集元信息**：目标库、时间窗、粒度、采集节点、分批情况、缺失维度、语义层是否降级。

涉及 DDL 落地时输出 `fix_plan` 并转 `safe-ddl-review` 做破坏性分级与审批要求确认。
调用 `terminate` 返回 1-2 句摘要（最大风险 + 最优先一条治理动作 + "均为提案，未执行"）。

## 完整流程示例

```
问题：生成 orders_prod 的数据库 profile 与治理建议（时间窗：最近 30 天，分段采集）

Step 1: db_metrics(target_db="orders_prod", time_window="<最近 30 天>", granularity="6h",
                   metrics=[disk_usage,data_size_bytes,index_size_bytes,table_count,
                            disk_io_util,replication_lag,backup_duration],
                   aggregate=[avg,p95,max], compare={baseline:"previous_period"})
  → 库体积 62GB（数据 44GB / 索引 18GB，比值 0.41）；磁盘使用率 84.2%，30 天 +11%
    备份窗口 48min → 71min（30 天内）；表数 214

Step 2: index_info(target_db="orders_prod", tables=<体积 Top 20>,
                   include=[row_count,size_bytes,columns,cardinality,unused,duplicate])
     schema_link(target_db="orders_prod", tables=["orders","order_items","order_log","order_snapshot"])
  → orders：19.2M 行 / 24GB / 索引 6GB；碎片率 8%；有主键；索引 4 个（1 个未使用）
    order_log：86M 行 / 19GB；碎片率 41%；**无主键**；含 TEXT 列 detail(平均 3.2KB)
    order_snapshot：4.1M 行 / 9GB；含 LONGBLOB payload(平均 180KB)，与热数据同表
    order_items：52M 行 / 8GB；碎片率 12%；索引 7 个（2 个重复）

Step 3: semantic_search(query="order_log order_snapshot 业务归属 下游 引用 owner", layer="mysql_prod", top_k=5)
  → order_log：审计用途，仅风控离线任务读取（冷）；order_snapshot：客服系统读取最近 90 天（半热）

Step 4:（问题定级）
    [P1] order_log 无主键 + 86M 行 + 碎片 41% ⇒ 复制回放慢、无法安全 Online DDL
    [P1] 冷热混存：order_log 90 天前数据占比 ~92%（间接推断，需业务确认），全部躺在主库
    [P1] 磁盘 84.2%，30 天 +11% ⇒ 线性外推约 45 天达 90% 告警线、约 5 个月触顶；备份窗口已 +48%
    [P2] order_snapshot 大字段（LONGBLOB 180KB）与热数据同表 ⇒ 缓冲池效率低、扫描代价高
    [P2] order_items 索引冗余（2 个重复、索引数 7）⇒ 写入放大，转 index-advisor
    [P2] 表注释覆盖率 38% ⇒ 可维护性

Step 5: 治理路线图
  A 立刻可做：order_items 重复索引清理提案（转 index-advisor，L1-L2，需审批）；
              应用侧停止 SELECT * 拉取 payload/detail 大字段；补齐 Top20 表注释
  B 需变更窗口：
     [B1] order_log 归档：新建 order_log_archive（同结构 + 主键 id），按 id 区间分批搬迁
          （每批 50 万行、间隔 2s、复制延迟 >30s 即暂停），搬迁后校验行数与抽样一致，
          保留 30 天可恢复期再清理源数据 ｜ L2→L3（清理阶段不可逆）｜ 生产 deny，需变更单
     [B2] order_log 补主键：随归档重建一并完成（单独改主键 = 重建 86M 行表，代价过高，不单独做）｜ L3
     [B3] order_snapshot 垂直拆表：payload 外置对象存储，库内留 URL + 摘要；
          或拆 snapshot_meta(热) / snapshot_payload(冷) ｜ L3 ｜ 需应用改造
     [B4] 碎片重建：仅在 B1/B2 完成后对剩余热表做，需等量空闲空间与 4h+ 窗口 ｜ L2
  C 架构演进：审计类日志迁出业务库（独立日志库/数仓）；读写分离扩容只读节点承接报表；
              评估按时间分区（orders/order_items）以支持分区裁剪与快速归档

Step 6: 产出 diag_report（profile 形态，含台账 + 趋势 + 路线图 + citation）
  terminate(result="orders_prod 画像：62GB/214 表，磁盘 84.2%（约 45 天达告警线）；三大 P1 为 order_log 无主键+碎片 41%、冷热混存（90 天前占 92%）、容量增速 11%/30 天。首选治理动作为 order_log 分批归档并补主键；全部为提案，未执行。")
```

## 注意事项（含安全红线）

- **只出画像与提案**：本技能默认**只调只读工具**（`db_metrics` / `index_info` / `schema_link` / `semantic_search` / `explain` / `slow_log`）。归档、重建、补主键、拆表、分区都属结构变更，走 `fix_plan` 提案 + `safe-ddl-review` 评审；`ddl` 受控且**生产命中 deny**，不得发起调用。
- **数据删除类动作是 L3 不可逆**：必须"先归档 → 校验行数与抽样 → 保留可恢复期 → 再清理"，且分批、可中止、可回滚。任何"直接 DELETE 历史数据"的建议都不合规，必须写成分批搬迁方案。
- **不得用 `truncate` / `drop_database`**：二者在套件 `tools.deny` 中；`DROP/TRUNCATE/RENAME` 形态的 DDL 亦被套件层永久拒绝。
- **审批被拒后不绕行**：不改参数重试、不拆批规避阈值、不借"归档任务"名义执行删除。
- **碎片重建有前置条件**：需要约等量空闲空间（重建期间双份占用）与足够窗口，且会推高复制延迟。磁盘余量不足时**禁止**建议重建，改为先归档腾空间。
- **冷热判定要标来源**：直接按时间列统计得到的是事实；由查询模式间接推断的必须标注"间接推断，需业务确认"，并建议与业务/风控 owner 核对保留策略（合规留存期可能禁止归档删除）。
- **采集分批限流**：表级明细每批 ≤20 表，避免元数据查询压垮生产；优先只读从库，采集自主库时报告标注。
- **外推要克制**：容量外推 ≤90 天，样本点 <3 标"不可信"；不承诺精确触顶日期，给区间。
- **不越界**：分库分表、异地多活等属架构演进（C 层），只给评估方向与前置条件，不在本技能内出实施方案。
- **工具连续 2 次同类失败**即停止重试，报告缺失维度并请求授权或补充信息。
- 工具白名单以套件 `tools.allow` 为准；**无 `shell`**，不得用脚本/命令行绕过工具做数据搬迁或删除。
