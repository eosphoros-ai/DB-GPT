# 构建经营仪表板

一屏按“现状如何 → 变化如何 → 为什么变”组织经营信息。适用于持续跟踪一组
指标；一次性取数用智能取数，需要叙述和建议的复盘用 `/analyze` 或 `/report`。

遵循[连接与口径检查](references/connector-readiness.md)、
[数据质量门禁](references/data-quality.md)与[数据证据卡](references/evidence-card.md)。
这些参考文件必须随本技能预加载；读取指令不代表检查已经执行。

## Step 0 — 连接器就绪性检查

- 确认当前选中的数据库、上传数据集或可用连接器及其可见表范围。
- 单个可用数据源即可开始，不因另一个连接器未接入而中断。
- 使用当前数据源的真实方言；不要把 Trino、MySQL、SQLite、Elasticsearch
  的语法混用。不存在或无权限的数据源不得声称已访问。
- DB-GPT 原生 Dashboard 当前绑定一个数据源。用户要求跨 Provider 时，
  明确范围限制，先交付已绑定源的可用部分，不混算不同源的同名指标。

## Step 1 — 明确使用决策

缺什么问什么，一次只问一个关键问题：

1. 谁看、看完做什么决策？
2. 业务范围、绝对时间范围与小时 / 天 / 周粒度是什么？
3. 核心指标是什么？用户未指定时，先发现元数据，列出 5–8 个有字段依据的
   候选指标供选择，不直接猜测并生成大盘。

目标值、阈值、刷新频率和筛选维度按需补充。已经提供的信息不重复询问。
用户明确列出的指标和视图优先，不能为满足模板数量而新增不相关指标。

## Step 2 — 发现数据源与指标口径

使用已注入的 schema、时间字段样本和语义中心上下文，按业务词定位表与字段。
只做必要的只读发现查询，规划轮最多八次 `sql_query`。
对接入多个文件的数据集检查来源清单、粒度、关联键重合度及 join 基数；
先按目标粒度聚合，防止事实表连接放大数值。

优先使用已发布的指标定义，记录定义来源及版本。未检索到定义或当前执行器
未提供知识库检索工具时，明确标注“口径未经语义中心确认”，展示拟采用的
定义和可选替代口径。不能把字段名当作已经确认的业务定义。

每个入选指标必须明确分子、分母、过滤条件、去重键、时间归属、单位与
对比基线；口径进入规划说明和最终看板业务说明，未定义清楚不能画图。

## Step 3 — 数据质量门禁

按参考文件检查 L1 结构、L2 新鲜度、L3 完整性、L4 唯一性。
可将检查合并进必要的发现 SQL，避免重复扫描。

- `BLOCKED`：不生成受阻指标。交付可用部分和阻断原因；全部受阻时停止生成。
- `READY_WITH_CAVEATS`：继续，但把 caveat 原样写进数据状态与相关指标说明。
- `READY`：继续。

记录真实查询依据。源数据是历史样例时展示其实际截止日期，不将样例旧日期
误判为业务系统故障，也不声称它是今天的实时经营数据。

## Step 4 — 设计信息层次与选图

| 层 | 内容 | 数量建议 |
| --- | --- | --- |
| L1 KPI | 当前值、对比基线、变化方向和已提供的目标 | 3–6 个 |
| L2 趋势 | 核心指标随时间变化 | 2–4 张 |
| L3 结构 | 渠道、品类、地域或门店贡献 | 2–4 张 |
| L4 明细 | 有权限且确有决策用途的下钻样本 | 按需 |

第一屏优先 L1 + L2。数量是建议；简单请求先规划 3–4 个核心组件，
不把所有层和所有建议数量叠加成默认交付范围。

趋势用折线 / 面积图，分类比较用按值排序的横向条形图，构成用堆叠条形图
（分类不超过五类才考虑饼图），关系用散点图，单值达成用 KPI 加对比。
仅选择运行时支持的图表类型，不支持的视图说明降级方式。

柱状图数值轴从 0 开始；双轴图分别标单位；颜色编码有图例；
同一指标在同一看板只采用一个口径。每个图有标题、单位与时间范围。

## Step 5 — 筛选、时间与状态

筛选只改变数据范围，不改变口径。会改变口径的筛选必须说明差异。
选项来自真实数据；日期范围使用两个独立参数，多选使用参数化 `IN`，
不拼接 SQL、不用字符串模糊匹配模拟多选。

说明数据截止时间、当前快照的绝对范围、已确认的数据延迟与刷新方式。
未配置定时任务时不能声称自动刷新；用户需要定时更新时说明需要另外配置。
空状态显示“该范围内无数据”；查询失败显示错误原因，不把失败当作 0。

## Step 6 — 使用 DB-GPT 原生看板流程

本指令复用服务已加载的 Dashboard Builder 流程：

1. 新建：用 `plan_dashboard(plan=...)` 提交无 SQL 的计划，把决策、口径、
   数据质量状态、截止时间和布局理由写入计划的业务说明。提交后结束本轮，
   让用户在原生规划卡上确认。不能在规划轮直接生成组件 SQL。
2. 确认：收到 `[[confirm-dashboard:ID]]` 后按持久化计划的真实组件 id、
   dashboard_id 与 expected_revision 调用 `create_dashboard_draft`，
   每次最多两个组件，仅补齐缺失组件。SQL 必须只读、参数化且字段映射一致。
3. 修复：仅用 `repair_dashboard_draft` 修复失败组件，保留成功组件。
4. 调整规划用 `revise_dashboard_plan`；现有草稿修改先
   `load_dashboard_draft`，再按版本合同调用 `modify_dashboard_draft`。
5. 批注说明复用已保存的证据；修改建议走 `propose_dashboard_change`，
   由用户在 UI 中审阅应用，不静默发布。

原生产物是可恢复、可预览、可编辑的 Dashboard 草稿。不能用一次性 HTML
报告替代原生看板。外部网页发布和单文件 HTML 导出不是本指令已实现的能力，
未发布不得声称已发布。

## Step 7 — 视觉与证据 QA

验证 KPI 的对比基线和方向、图表标题 / 单位 / 范围、轴与图例、口径一致性、
筛选参数、空状态、错误状态与数据质量说明。每个关键数字关联真实执行 SQL，
过滤范围与结论范围一致，不由子集外推全集；截断明细不得用来计算占比和排名。

最后用工具结果确认所有请求组件的生成状态。只完成规划不能说仪表板已建成。
如有失败，交付成功部分与缺失视图，附[十项数据证据卡](references/evidence-card.md)。
输出开头给一句结论，末尾仅列本次实际使用的数据源展示名。
