# 运维报告

目标：让看报告的人**在 30 秒内知道要不要管、管什么**，让报告能被直接转成工单。指标堆砌的周报没有价值。

阈值判定沿用：[指标阈值基准](../mysql-ops-knowledge/references/metrics-thresholds.md)
安全与脱敏：[安全红线与执行分级](../mysql-ops-knowledge/references/safe-execution-rules.md)
版式：[报告模板集](references/report-templates.md)

## 第 1 步：确定报告类型与读者（决定一切写法）

| 类型 | 读者 | 长度 | 重心 | 触发词 |
|:---|:---|:---|:---|:---|
| **日报** | DBA / 值班 | 1 屏 | 昨天异常 + 今日待办 + 红黄项变化 | 日报、今天情况 |
| **周报** | DBA + 研发负责人 | 1–2 页 | 趋势 + 治理进度 + 下周计划 + 需要谁配合 | 周报、本周总结 |
| **容量报告** | 架构 / 预算决策者 | 1–2 页 | 增长曲线 + 触顶时间 + 扩容建议与成本 | 容量、扩缩容、要不要加机器 |
| **故障复盘** | 全团队 | 按模板 | 时间线 + 根因 + 改进项（转 @故障应急） | 复盘、事故报告 |
| **向上汇报** | 非技术管理者 | **半屏** | 稳定性结果、风险与要的资源；**几乎不放指标** | 给老板看、月度总结 |
| **治理专项** | 业务方 | 按对象 | 谁的问题、改什么、收益、时间点 | 慢 SQL 治理、无主键清理 |

**关键规则**：向上汇报里不出现 `Threads_running`、`Innodb_log_waits` 这类术语；技术报告里不出现"加强了、提升了、整体平稳"这类无数据表述。

## 第 2 步：收料（缺料时的正确姿势）

优先输入的素材（有多少用多少）：巡检报告（@实例巡检 产出）、故障记录/@故障应急 复盘、慢 SQL 治理清单、变更单记录、告警明细、容量数据（磁盘/连接/QPS 历史）。

**料不够时的正确做法**（不允许编数字）：
1. 明确列出"本报告缺以下数据：`<项>`，需 `<来源/命令>`，补齐后更新结论"；
2. 用"无法判定"替代猜测，并在报告里显式标注；
3. 只基于已有数据给结论，且**结论强度与数据完整度匹配**（数据只有磁盘 → 不要写"整体稳定性良好"）。

## 第 3 步：写作规则

1. **结论先行**：第一段必须是判断句（"本周数据库整体🟡，风险集中在容量与慢 SQL 治理进度滞后"），不是流水账。
2. **一切量化**：每个论断带数字与对比（"慢查询数 0.4/s → 2.1/s（+425%），与 10-23 `<发布单>` 时间吻合"）。
3. **变化优先于状态**：只报"变了什么"和"要变了"。长期平稳的项目一行带过，不要凑篇幅。
4. **趋势要有预测**：容量类必须给"按当前斜率何时触顶"（"648GB，+5.9%/周 → 预计 11-20 触顶"），并给不确定区间。
5. **每项问题可认领**：责任人、动作、时间点、验收标准。写不出责任人的项 = 还没想清楚，别写进报告。
6. **闭环上期**：上期承诺的每项改进，本期必须标注 `已完成 / 进行中（进度）/ 延期（原因+新时间）`。**这是报告可信度的核心**。
7. **风险要说人话**：技术风险翻译成后果（"数据盘 8 天后满 → 实例被锁为只读 → 下单和支付写入全部失败"）。
8. 数据脱敏：账号、IP、库表名、业务字段值按红线文件处理。
9. **不粉饰**：故障就是故障。写"影响 27 分钟、失败请求 N 万次"，不写"短时波动"。

## 第 4 步：按类型套模板

从 [报告模板集](references/report-templates.md) 选对应版式：日报 / 周报 / 容量 / 向上汇报 / 治理专项。
通用必备结构：**执行摘要 → 关键指标变化 → 风险与问题（可认领清单） → 上期跟进闭环 → 下期计划 → 需要的支持/决策**。

**执行摘要写法规矩**（决定报告是否被看完）：
- 3–5 条，每条一句一个结论；
- 顺序按"需要读者做决定的紧迫度"排，不按时间或模块排；
- 至少包含：整体评级（🟢/🟡/🔴）、最危险的 1–2 个风险及其后果、需要谁决策什么。

## 第 5 步：跟进闭环

报告不是终点。产出后主动做：
1. 把"问题清单"整理成可直接批量建单的表格（每条含标题、描述、优先级、责任方、期望完成）；
2. 提醒哪些条目属于**临时措施待回退**（最易遗漏，也是二次故障的常见来源）；
3. 建议报告的**投递节奏与归档位置**（如每工作日 09:30 → 群 + 文档目录固定路径），并给出可用定时任务自动跑的方案；
4. 给出下一期报告的"本期承诺项"，形成周期间咬合。

## 常见反模式（写作时自检）

| 反模式 | 改成 |
|:---|:---|
| "数据库整体运行平稳" | "本周无 P0/P1 故障；磁盘使用率 72%→79%（+7pt），预计 11-20 触顶" |
| 罗列 30 个指标不给判断 | 只列 5 个**变了**的指标 + 每个的判定与动作 |
| "建议优化慢 SQL" | "`<digest a1b2c3d4>` 扫描 124 万行/次，占库总耗时 47%；加 `(status,id,gmt_create)` 预期 p95 8.2s→150ms；责任人 `<订单服务>`，11-05 前" |
| 只报问题不报进度 | 上期 6 项：完成 4、延期 2（原因 + 新时间点） |
| 向上汇报放技术细节 | 三段：结果（几个月可用率）/ 风险（业务后果 + 概率）/ 要什么（资源或决策） |
| 风险清单没有时间点 | 每条都有"何时不做会发生什么" |

## 边界

- 不虚构数据、不推断未采集指标。
- 不把"建议"写成"已做"。
- 报告的结论若与 @实例巡检 / @故障应急 的判读冲突，以阈值基准为准并显式说明差异来源（通常是时间窗口不同）。

## If Connectors Available

If **监控指标** 已连接：
- 自动拉取周期曲线并计算环比/同比与增长斜率，容量预测无需手工导数据。

If **文档平台** 已连接：
- 报告自动发布为文档并归档到固定目录，形成可追溯的历史序列。

If **任务工具** 已连接：
- 问题清单批量建单并指派；上期跟进项状态自动回填到本期报告。

If **沟通工具** 已连接：
- 摘要（评级 + 红项 + 待决策）按节奏推送到群，全文以链接给出。

If **知识库** 已连接：
- 报告与巡检记录、复盘文档互相引用，形成单一事实来源。

If 无连接器（默认）：
- 落盘 `outputs/report-<类型>-<YYYYMMDD>.md`；表格可直接复制到工单/群内。
