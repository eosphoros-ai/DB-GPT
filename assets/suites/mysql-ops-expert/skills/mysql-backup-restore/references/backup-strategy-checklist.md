# 备份策略评估清单

评估产出的核心不是"备份做了几套"，而是三个问题的答案：**能恢复到什么时候（RPO 实际值）、要多久（RTO 实测值）、谁验证过（演练记录）**。

## 第 0 步：30 秒快查（出事时先跑这几条）

```sql
SHOW BINARY LOGS;                                   -- binlog 是否连续、最早文件时间
SELECT @@log_bin, @@binlog_format, @@binlog_row_image,
       @@binlog_expire_logs_seconds, @@expire_logs_days, @@sync_binlog;
SELECT @@innodb_file_per_table, @@innodb_data_home_dir, @@datadir;
SHOW REPLICA STATUS\G                               -- 是否有可用从库/延迟从库
```
```bash
ls -lhrt /backup/mysql | tail -20                   # 最近全备时间与大小
find /backup -name xtrabackup_info -mtime -30 | head # 备份元信息
du -sh /var/lib/mysql                                # 数据量（决定恢复耗时）
```
**云 RDS**：控制台 → 备份恢复 → 备份列表（看全备时间/大小）+ 日志备份是否开启 + 保留天数 + 是否有跨地域备份。

## 第 1 步：备份链完整性（最常见的隐性缺陷）

| 检查项 | 判定 | 不通过的后果 |
|:---|:---|:---|
| 全备**内记录的 binlog 位点** ≤ 当前保留的最早 binlog | 读 `xtrabackup_binlog_info` / `xtrabackup_info` | **中间断档 → 无法 PITR 到该区间**（表现为"有备份但恢复不到昨天下午"） |
| binlog 序号连续无缺失 | `SHOW BINARY LOGS` 比对 | 断点导致恢复链在任意缺口处终止 |
| 全备期间写入的 redo 可 apply | `xtrabackup --prepare` 输出 `completed OK!` | 备份集不可用（**没 prepare 过的备份等于没备份**） |
| 全备时间窗口内无 `PURGE BINARY LOGS`/`RESET MASTER` | 变更/操作记录 | 自毁恢复能力 |
| 备份文件与生产**不同机** | 路径与主机核对 | 同盘故障一起丢 |
| 至少一份异地/异 site 副本 | 副本清单 | 机房级事故全丢 |
| 备份有访问权限隔离（非生产账号可删） | 权限清单 | 误删/勒索无退路 |

## 第 2 步：RPO / RTO 对齐

**RPO（可容忍丢多少数据）**
| 配置 | 实际 RPO |
|:---|:---|
| `sync_binlog=1` + `innodb_flush_log_at_trx_commit=1` + 异步复制 | 主库盘完好≈0；**主库整机损毁 → 丢最多一个 binlog 缓冲（可达秒级/数十秒）** |
| 同上 + after_sync 半同步（多数派确认） | 接近 0（网络分区降级期间退化为异步，需监控降级事件） |
| `sync_binlog=1000` 或 `trx_commit=2` | 主机崩溃可能丢 1s 级事务；`sync_binlog=1000` 丢更多 |
| 只有每日全备、无 binlog | **RPO = 最多 24h**（多数团队实际是这个，且不知道） |

**RTO（要多久恢复）实测口径**：`恢复 = 下载备份 + 传输 + prepare + 启动回放 binlog + 校验 + 切流量`
粗估：xtrabackup 恢复 ≈ **数据量 ÷ 磁盘顺序读/写吞吐（保守 100–150 MB/s）**，binlog 回放时间与"全备到目标点的事务量"正相关（往往比全备恢复更久）。
> **必须给团队一个实测数字**：跑一次真实演练并计时。经验上"以为 1 小时"的实际是 4–8 小时（备份下载 + 大 binlog 回放被严重低估）。

## 第 3 步：备份方式是否匹配场景

| 场景 | 需要 | 只有另一种的风险 |
|:---|:---|:---|
| 整库灾难恢复 | 物理备份（xtrabackup / 云快照） | 只有 mysqldump：TB 级恢复需数十小时 |
| 单表/单行误删 | 逻辑备份或 binlog 行事件 | 只有物理备份：需恢复整库到临时实例再抽表（慢但可行） |
| 跨版本/迁移 | 逻辑备份（`mysqldump --set-gtid-purged` 按需）/ DIML | 物理备份不跨大版本 |
| 合规长期归档（3–5 年） | 定期导出 + 介质可复用性验证 | 云快照过期即无 |
| 数据一致性要求高（对账） | 全备 + binlog + 延迟从库 | 快照备份 LSN 一致性需 `--lock-all-fds`/FLUSH 处理 |

## 第 4 步：高频缺陷清单（逐条问"我们有吗"）

- [ ] **无延迟从库**（`CHANGE MASTER TO SOURCE_DELAY=3600`）：误删场景成本最低的救命通道。
- [ ] **备份只在本机**：与生产同盘/同机，等于单点。
- [ ] **从库做备份但没人校验**：从库本身可能已不一致。
- [ ] **备份成功率无人看**：磁盘满/超时/权限导致连续 N 天失败而无人知（**必须有"备份成功率 + 备份大小突变"告警**）。
- [ ] **备份大小异常未察觉**：突然变小 30% 通常是备份工具部分失败或被截断。
- [ ] **binlog 保留期 < 全备周期**：例如全备每周一次、binlog 只留 3 天 → **中间有 4 天无法 PITR**（典型致命组合）。
- [ ] **无恢复演练记录**，或演练只做了 `--prepare` 没做完整链路。
- [ ] **加密/压缩备份的密钥丢失**（KMS 轮换后旧备份解不开）。
- [ ] **`GTID_MODE=OFF` 的环境做 PITR**：位点管理复杂、易出错（→ 建议开 GTID）。
- [ ] **DDL 与备份撞车**：备份期间大表 DDL 导致备份失败或恢复异常。
- [ ] **云：日志备份被关**（为省钱关闭 → 只剩全备，RPO 变 24h）。
- [ ] **云：无本地下载副本**，只有云侧快照（供应商故障即不可用）。
- [ ] **无主键大表**：单表恢复与订正极难（见索引手册 I-20）。

## 第 5 步：输出格式

```
# 备份能力评估：<实例/集群>
## 结论
- 实际 RPO：<X>（业务要求：<Y>）→ 满足 / 不满足
- 实测 RTO：<X>（业务要求：<Y>；未演练则标注"估算，需演练验证"）
- 备份链：<完整 / 存在断档：<区间>>
- 整体判定：🟢/🟡/🔴
## 缺口清单（按风险排序）
| # | 缺口 | 故障场景（具体化） | 影响 | 修复动作 | 成本 | 优先级 |
## 建议的备份矩阵
| 对象 | 方式 | 频率 | 保留 | 存放 | 校验 | 演练 |
## 演练方案
- 频率：每季度 1 次（关键库每月）
- 内容：全备恢复 + binlog 回放至指定时间点 + 一致性校验 + 计时
- 验收：实测 RTO ≤ 目标；输出演练报告与签字
- 自动化：可脚本化项（下载→prepare→启动→校验→计时）列表
```

**写故障场景要具体**："周三下午 3 点误删订单表 12 万行时，我们只能回滚到当天 02:00 的全备，丢 13 小时数据" —— 这种描述能推动决策，"RPO 不满足要求"不能。
