# 内置 Flow、语义中心与并行执行评审

评审日期：2026-11-01。评审对象为当前工作区源码与 localhost:3000 / localhost:5670 服务。本轮新增验证脚本、证据和评审文档，未修改模板、执行器或已保存工作流。

结论：三个 DB TaskFlow 应接入语义中心；当前没有真正并行的双 Agent 内置模板。优先修正工具配置和口径传递，再改造编译器与调度器实现并行。

HTTP 200 仅表示流式接口接收请求。本轮两次模型试运行均未完成，未确定超时根因，不能据此认定模型已执行工具或数据分析成功。此前会话出现过订阅/余额错误，但本轮没有收到相同错误，不能把旧错误作为本轮原因。

调度实验使用真实默认 AWEL 执行器及计时 MapOperator，模型调用被替换为等待操作，仅验证调度行为。电商数据来自工作区已有的 **Semantic_Commerce_Case 合成样例**，不是生产数据，也不是本轮新造数据。

## 为什么要接入最新语义工具

当前可用工具为：

- `semantic_get_metadata`：读取当前数据库表、字段、同步时间与治理标记。
- `semantic_search_business`：检索已发布的业务定义和同义词。
- `semantic_search_metrics`：检索已发布指标候选，识别多个可能口径。
- `semantic_get_metric`：获取明确指标的指定发布版本，携带引用；版本不存在时不回退。

现有 TaskFlow Agent 的 `SELECTABLE_TOOLS` 及 `make_react_tools` 没有接入这些工具。仅修改节点提示词或把工具名写进模板，不能使工具实际可调用。

本轮直接调用工具读取当前服务使用的元数据库：

| 数据源 | 元数据表数 | 已发布业务定义数 | 已发布指标 |
|---|---:|---:|---|
| Olist_Ecommerce | 12 | 0 | 0 |
| Walmart_Sales | 1 | 0 | 1：cnt_walmart_sales |
| Semantic_Commerce_Case | 7 | 11 | 5 |

因此，“语义中心已激活”不等于“销售额、订单额等业务口径已经发布”。没有定义时应说明缺口并澄清，不能把 Agent 对字段名的推测包装成受治理口径。

电商样例实际读取发布快照并执行其中 SQL：

| 指标 | 金额 | 发布引用 |
|---|---:|---|
| 成功支付额 | 413 元 | semantic::Semantic_Commerce_Case/metric/14@v1 |
| 成功退款额 | 45 元 | semantic::Semantic_Commerce_Case/metric/15@v1 |
| 净实收_含运费对照 | 368 元 | semantic::Semantic_Commerce_Case/metric/16@v1 |
| 净实收 | 338 元 | semantic::Semantic_Commerce_Case/metric/17@v1 |
| 有效GMV | 400 元 | semantic::Semantic_Commerce_Case/metric/18@v1 |

338 元与 368 元对应两个不同指标，发布版本均为 v1；不能误说成当前服务中同一指标的历史 v1/v2。净实收涉及运费、退款、状态和租户过滤等定义，直接做“支付额减退款额”会得到含运费对照口径。

## 每个模板的调整建议

| 模板 | 当前结构 | 建议结构与职责 |
|---|---|---|
| DB 数据取数 | 3 个串行 Agent：接地、SQL 取数、结果整理 | 语义解析 → 确定指标版本/筛选/粒度 → SQL 查询 → 表格及来源说明。简单取数可由一个 Agent 调用多个工具完成，减少不必要的模型接力 |
| DB 智能分析 | 5 个串行 Agent：接地、计划、分析、复核、报告 | 口径与范围确认 → 计划 → 趋势分析与质量检查并行 → 汇总复核 → 报告 |
| DB 数据库答疑 | 2 个串行 Agent：接地、答案组织 | 表结构问题读 metadata；业务定义读 business；指标问题 search_metrics 后 get_metric；外部知识库作为补充来源。短问答可合并为一个 Agent |
| 传统 Chat Data/text2SQL | 传统数据库检索与 SQL 生成链 | 在生成 SQL 前补语义解析阶段，向 SQL 生成节点传递确定的口径快照；检索表结构无法替代指标定义 |
| 普通对话、RAG、知识加工 | 对话/知识检索/嵌入等传统 AWEL | 保留原用途；涉及数据库指标时调用语义中心，不把普通知识库检索结果自动认定为发布口径 |

建议跨节点传递结构化证据：`conn_id`、同步时间、表字段、`metric_id`、发布 `version`、`citation`、时间范围、时区、单位、粒度、过滤条件、SQL、结果和核验结论。后续节点沿用同一版本，避免执行过程中各自读取“最新”导致口径变化。

复核应独立检查 SQL、过滤条件、连接基数和数字。对于已发布的权威口径 SQL，应保持语义等价；不必强制每次换写法。报告只能采用核验后的数字，保留可点击或可定位的来源。

## 需要先修的配置问题

1. 取数和分析模板中 `code_interpreter` 应改为当前运行时名称 `code`，目标提示词同步修改。当前未知工具会被静默过滤，编译通过并不等于工具可用。
2. 分析模板指定 `sql-data-analysis`，但服务 `agent-options.skills=[]`。应安装并确认注册，或从模板移除强制依赖；实例化时显示资源缺失。
3. 三个模板固定 `Walmart_Sales`。实例化应选择数据源并一致绑定所有需要查询的节点；语义工具也必须绑定同一个已授权数据库，不能让模型随意切换连接。
4. 答疑模板采用“必须先检索知识库”的 persona，却未选择知识库。需调整为语义中心优先，知识库按实际配置补充。
5. “禁止全表扫描”与“获取行数、枚举分布”等要求可能冲突。应优先使用元数据/统计信息，探查与正式统计分别设置时间、行数、资源预算；LIMIT 不一定减少聚合扫描。
6. 编译或实例化阶段应校验未知工具、缺失技能和数据源，给出明确错误，避免静默降级。
7. 原回归测试应改为覆盖实际模板目录；编译/DAG 测试之外增加资源一致性和语义引用传递检查，避免模板更换后测试长期失效。

## 两个 Agent 可以在哪些场景并行

**当前没有可直接使用的真正并行模板。** 数据库答疑虽然有两个 Agent，但第二个依赖第一个的结果，适合串行。

推荐优先实现智能分析中的两个独立分支：

```text
确定问题、数据源、指标版本和分析计划
                 ├─ Agent A：趋势、对比、贡献分析 ─┐
                 └─ Agent B：空值、重复、关联质量 ─┤
                                               汇总复核 → 报告
```

两分支读取同一份口径和时间范围。数据质量结论可以约束报告可信度，趋势结论给出业务发现；它们不需要等待对方输出。

其他候选：

- 数据库答疑：元数据核查与业务定义/指标检索并行，再合并证据回答。
- 固定指标分析：两个 Agent 按同一口径分别计算和独立核验，再比较差异。

“核验上游分析结论”必须等待结论生成，不能直接与该分析节点并行；如果要并行，应把核验任务改为基于已确定指标清单的独立计算。

## 真正并行需要改哪些层

1. **编译器**：依据声明的前驱/可达祖先建立数据依赖。当前连接所有拓扑顺序在前的节点，会把兄弟分支串起来；现有串行模板需要保持上下文兼容。
2. **执行器**：默认 runner 逐一 await 上游节点，应增加依赖就绪后的有界并发。不能只把循环换为 gather：共享 `DAGContext.current_task_context`、公共祖先重复执行、状态写入、失败取消均需处理。
3. **汇合语义**：明确等待哪些分支、分支失败如何处理、结果如何按节点归属合并。`parallel_with_prev` 目前只是被接受的保留配置，不具备执行作用。
4. **界面**：按节点 ID 更新实时状态与工具时间线，允许两个节点同时显示运行；完成次序不能改变结果归属。
5. **验证**：检查执行区间重叠、公共祖先只运行一次、并发限制、分支取消与失败传播、证据归属，以及原串行流程结果。

并行收益取决于模型和查询耗时，不能仅根据节点数估算。此次 200ms 探针揭示的是当前串行行为，不是实际模型提速基准。
