# 对话生成 Agent 工作流：工程落地建议

这是前期工程分析，保留实施前的仓库结论。首版已接入产品源码，当前行为与验证以 [实现与验证记录](implementation-verification.md) 为准；同目录 HTML 是交互原型。

多轮需求确认、持续修改、会话状态、接口协议及并发规则已整理为独立的 [多轮对话技术方案](multi-turn-workflow-technical-design.md)。相关设计以该文档为准，本文保留前期仓库分析与改动规模说明。

## 改动规模判断

首版限定串行多 Agent 时，整体是中等规模扩展，不需要重写 AWEL 或通用 Agent 执行器。主要成本在生成入口、可靠状态同步、资源校验和发布版本隔离。

| 模块 | 改动程度 | 建议 |
| --- | --- | --- |
| 编辑器 | 中 | 增加对话面板、候选预览和统一草稿状态，复用画布与配置面板 |
| 生成服务 | 中，新增 | 基于现有模型调用链生成结构化 DSL，增加澄清、校验、候选应用 |
| 能力与资源目录 | 小至中 | 复用现有目录，补齐用户范围、默认能力与执行策略校验 |
| TaskFlow DSL | 小 | 首版沿用 `taskflow/1` 和 `agent`，输入输出约定先写入目标 |
| AWEL 与 Agent 操作符 | 小 | 复用现有编译执行链；补首版顺序约束与能力限制 |
| 试运行 | 小至中 | 复用临时调试接口，修正状态判定，补快照版本与成功验证记录 |
| 草稿 / 发布隔离 | 中，需改生命周期 | 独立草稿与不可变发布快照，避免编辑替换线上 DAG |
| 并行、分支、循环、真实审批 | 大 | 同时改变 DSL、编译器与运行状态，留到后续 |

上述程度是根据代码结构的相对判断，不是工期或人力承诺。

## 现有可复用基础

- `web/pages/taskflow/editor.tsx`：工作流元信息、DSL 状态、节点操作、保存与发布入口；自然语言栏目前是占位。
- `web/components/taskflow/editor/PropertyPanel.tsx`：节点配置。
- `web/components/taskflow/editor/DebugDrawer.tsx`：向 `/api/v2/serve/awel/flow/debug` 提交当前未保存流程与运行输入；可以复用，不需要为试运行先发布流程。
- `web/types/taskflow.ts`：`ITaskflowDSL`、Agent 能力选项和运行标记。
- `packages/dbgpt-serve/src/dbgpt_serve/flow/taskflow/nodes.py`：Agent 节点支持 `agent_profile`、`goal`、`model`、`tools`、`skills`、`datasources`、`knowledge`、`mcp`、`max_turns`。
- `packages/dbgpt-serve/src/dbgpt_serve/flow/taskflow/compiler.py`：将 TaskFlow 编译为 AWEL。
- `packages/dbgpt-serve/src/dbgpt_serve/flow/taskflow/dsl.py`：DSL 解析与结构校验。
- `packages/dbgpt-app/src/dbgpt_app/operators/taskflow_agent.py`：运行时通用 Agent 操作符。

上述是已读取源码支持的基础。本文建议的接口、版本管理、生成会话和输入输出元信息需要新增或进一步核查，不应理解为已有能力。

## 推荐链路

用户描述 + 当前流程快照 + 可用能力目录
→ 生成服务解析目标与职责
→ 输出结构化候选
→ 服务端校验
→ 前端差异预览 / 首次生成进入草稿
→ 应用并更新版本
→ 现有 TaskFlow 编译与 AWEL 执行。

生成服务与执行器分开：生成阶段仅查询能力目录及授权范围，不调用业务 Agent 的工具。只允许生成已注册的节点、能力与资源引用。

首版内容节点限制为 `agent`，并保留 `start` 和 `output`。业务角色使用节点名称、画像、职责和能力配置表达，避免新增“销售 Agent”“图表 Agent”等执行节点类型。历史混合节点流程继续兼容；对既有流程局部修改时保持未受影响节点，整体迁移需要明确预览。

## 建议新增的生成与修改服务

推荐统一为一个会话服务，以下路由名称仅为候选设计：

- `POST /taskflow/generation-sessions`：建立会话，绑定工作流或未保存草稿快照。
- `POST /taskflow/generation-sessions/{id}/messages`：提交描述、作用范围、选中节点、当前版本及当前 DSL；流式返回阶段进度、澄清请求或完整候选。
- `POST /taskflow/generation-sessions/{id}/cancel`：取消生成；迟到的结果不得更新画布。
- `POST /taskflow/generation-candidates/{id}/apply`：核对基础版本与能力快照后，接受候选。已保存工作流的版本更新应为原子操作；未保存草稿返回校验后的结果及草稿版本。

响应建议采用区分类型的结构：

```text
type: clarification | candidate | failure
session_id
request_id
base_revision
summary
questions / candidate / error
```

候选结构：

```text
candidate_id
flow_meta
candidate_dsl
change_summary
assumptions
missing_configuration
validation_issues
```

完整候选 DSL 作为原子替换单位，服务端对比当前 DSL 计算差异，避免前端实现任意补丁执行器。稳定保留未改变节点的 ID；局部修改通过受影响节点和边集合审阅。客户端不信任模型自己声称的“已通过校验”。

对话记录、生成任务与候选是编辑辅助数据；DSL 是唯一执行定义。保存最近会话摘要和引用的工作流版本，使刷新后继续修改。原始消息保留策略待产品决定。

## 校验分层

1. **结构校验**：版本、合法节点类型、唯一 ID、唯一开始和输出、边引用合法、无重复边、无环。首版进一步要求单链、所有内容节点可从开始到达且可通向输出。
2. **内容校验**：每个 Agent 的目标与交接要求完整；选中画像和工具技能存在；能力能够完成本步目标。
3. **资源与策略校验**：数据源、知识库、模型和 MCP 来自真实可访问目录。首版允许范围由服务端执行策略落实，包含角色默认工具、技能脚本和 MCP 的实际行为。未知风险能力不自动放行。
4. **编译校验**：复用编译器确认可形成运行图。资源缺口允许保留草稿，但不能发布或试运行。确认编译器不会把空资源范围变成宽泛默认范围。
5. **运行验证**：绑定规范化 DSL 与元信息的版本或指纹、实际模型与能力配置版本、运行参数、状态和产物；成功记录仅证明该版本及本次输入验证通过，不保证所有输入都成功。

格式错误可进行有上限的生成修正；上限具体值待实现时配置。不能无限修正，也不能用部分生成内容覆盖当前流程。

## 前端改动边界

推荐新增：

- `ConversationPanel`：需求输入、生成进度、澄清、修改历史和上下文作用范围。
- `GenerationChangePreview`：新增、删除、配置变化、配置缺口、应用及放弃。
- 一个统一的工作流草稿状态层：同时服务手动编辑和对话应用，维护版本、脏状态、撤销快照、待应用候选及最新验证版本。

现有 `setDsl` 可以作为起点，但所有修改入口都应使草稿版本递增、运行验证过期。并发请求用请求 ID 和基础版本过滤，取消后的响应不被应用。

右侧配置复用现有字段。输入与输出约定首版可嵌入 `goal` 约束，并以编辑辅助元信息展示；若需要单独字段，必须同时明确它们的存储和编译映射，避免 UI 表单与运行时脱节。

## 编排语义限制

当前编辑器通过顺序遍历生成一条展示链，每个源节点在 `nextOf` 中只保留一个后继；不能直接当作分支编辑器。

当前编译器将前序节点的干净数据出口连接到后续数据入口。这与 Agent 的“全部上游产出”上下文约定一致，但不足以表达精准依赖与分支隔离。首版应明确这一语义。

并行、分支和循环需要同时升级：

- 编辑器布局、连线与控制节点模型；
- Agent 输入绑定、结构化产出与合并策略；
- 编译器的数据依赖和控制依赖；
- 运行快照、失败传播、暂停恢复和重试规则。

`retry`、`timeout_s`、`parallel_with_prev` 在现有 DSL 中属于预留但尚未接通的键，不能依赖它们实现首版编排。

现有 `HOHumanConfirmOperator` 是软确认透传。真正审批需要持久化运行状态、暂停点、确认者权限、恢复令牌和重复执行保护；完成前不作为写操作的授权节点。

## 草稿与发布版本

目前编辑器通过同一工作流对象的 `developing` / `deployed` 状态保存和发布；不能据此假定发布版本隔离已存在。

已进一步核实 `packages/dbgpt-serve/src/dbgpt_serve/flow/service/service.py`：

- `update_flow()` 编译新内容后，更新同一 UID 的实体，再调用 `delete()` 和 `create_and_save_dag()`。
- `delete()` 会注销对应 DAG 并删除实体；不是仅更新独立草稿。
- 因而保存同一 UID 的新内容不能作为“保留旧发布版本”的实现基础，需要调整生命周期。

建议工作流拥有可编辑草稿与不可变发布快照。正式运行只引用发布快照；试运行引用草稿快照。发布前校验基础版本、权限、当前版本成功运行记录与资源有效性。

若先沿用现有 API，必须先确认服务端存储与运行图缓存如何隔离，必要时补发布快照。不能仅给前端增加“已发布”标签就声称旧版本不会被草稿改动影响。

缩小首版范围的备选：只支持新建流程的对话生成，以及对已发布流程“另存为新草稿”。原发布 UID 不参与编辑更新。这样可先降低版本改造范围，但产品必须明确另存流程与原流程是独立对象；再次发布不会自动替换原流程。推荐完整版本仍采用同一逻辑工作流下的草稿与发布快照。

## 试运行状态修正

当前 `DebugDrawer` 的步骤摘要只要存在 marker 就标为成功，未直接使用 marker 的 `running` / `failed` 状态。为支持“当前版本成功试运行后发布”，必须按真实标记状态与最终服务端完成状态记录成功，不能将出现日志或流连接结束视为成功。

临时调试接口可以复用；发布验证需要服务端持有版本匹配的成功证据，不能仅使用前端按钮状态。

## 验证重点

- 无效候选、取消生成和迟到响应不能覆盖画布。
- 对话局部修改保留已有节点 ID、资源配置与手动修改。
- 生成期间的手动编辑导致旧候选不可应用。
- 不可访问或不存在的能力、模型、资源不能被绑定。
- 资源缺口可保存草稿，但不能运行或发布。
- 修改导致验证过期，发布必须匹配当前快照。
- 首版策略在工具执行层覆盖默认工具、技能和 MCP，不能仅使用提示词限制。
- 旧混合节点流程继续能加载；新增对话生成采用 Agent 内容节点。
