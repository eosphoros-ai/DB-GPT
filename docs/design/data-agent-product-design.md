## 一、产品定位与设计原则

**定位**：面向企业业务库（非数仓）的 Agentic 数据平台 —— 用自然语言完成 **取数、分析、运维** 三类数据工作，语义层与知识库保证准确率，审批与技能体系保证可控与可扩展。

**设计原则**：
1. **对话优先**：首页即一个大 composer，说需求自动路由到场景；不做重仪表盘首页。
2. **场景即工作台**：一级场景 = 独立工作台（左轨迹 / 中对话 / 右查看器），场景间不混排。
3. **语义层是地基**：所有问数/分析默认绑定语义模型，口径可见、可切换、可编辑。
4. **可控可审计**：高危/高代价操作走审批 dock；审批模式会话级可切；全程留轨迹与状态线。
5. **贴现有 UI**：不另起视觉体系，复用现有侧栏/首页/composer 范式，降低迁移成本。

## 三、场景体系（首页 Tab ↔ 工作台 ↔ 推荐问题）

首页用 **场景 Tab + 每场景推荐问题** 取代现有平铺 "RECOMMENDED EXAMPLES"。Tab 与工作台一一对应，点击推荐问题 = 填入 composer 并路由到对应工作台。

| 场景 Tab | 路由到 | 场景描述 | 推荐问题（示例） |
|---|---|---|---|
| **智能取数** | DB 取数工作台 | 自然语言→SQL，绑语义模型精准取数 | 查询上月各区域销售额 / 统计 Top10 客户 GMV 及环比 / 近30天各品类客单价 |
| **智能分析** | DB 数据分析工作台 | 数据集圈定→多步取数→图表→结论→报告 | 生成 Walmart 销售分析报告 / 分析本月销售下滑归因 / 对比华东华南订单占比趋势 |
| **智能运维** | DB 运维工作台 | 慢查询诊断/巡检/画像治理/修复确认 | 订单库昨晚慢查询根因 / 生产库健康巡检出报告 / 生成数据库 profile 与治理建议 |
| **技能与 Agent** | 技能模块 | 封装可复用 Skill / 定时 Agent | 用 skill-creator 创建 SQL 分析 skill / 创建定时经营报告 Agent / 封装一个取数 API 技能 |

> 对标阿里 DataAgent：其"智能问数/智能报告/数据洞察/归因/运维治理"的场景入口 + 每场景推荐问法，被收敛为上述 4 Tab（阿里"智能问数"改名"智能取数"以贴业务库取数场景、报告与洞察归入"智能分析"，治理归入"智能运维"），保证每个 Tab 点进去都有可跑的工作台，不出现空场景。

**路由规则**：composer 输入实时识别场景（关键词：慢查询/巡检/根因→运维；分析/归因/报告/趋势→分析；查/统计/导出/GMV→问数），识别结果以 chip 显示在 composer 内；场景 Tab 点击 = 显式指定，覆盖自动路由。

## 四、对话 & 场景预设模型（一个引擎 + 预设）

**核心结论**：三大场景共用**同一个 ReAct 引擎**（一个 reason→act→observe 循环）。场景之间的差异不在引擎，而在包在引擎外面的**六维场景配置束（preset）**。因此场景**不是入口、不是独立对话系统**，而是挂在对话上的预设标签 + 初始化配置。该配置束的可安装形态即专家套件（§5）：等价表述为**一个 agent + 三个套件**——套件是配置、agent 是执行器；套件与核心的边界见 §5.8。

### 4.1 六维场景配置束

| 维度 | 智能取数 | 智能分析 | 智能运维 |
|---|---|---|---|
| 角色 & SOP（system prompt） | 精准取数员：schema-link→SQL→执行→预览 | 数据分析师：圈数据集→多步取数→图表→结论→报告 | DBA：采集慢日志/EXPLAIN→聚合→根因→诊断→修复提案 |
| 工具白名单 | semantic_search、schema_link、nl2sql、sql_execute(只读)、export | 上述 + dataset_scope、chart、report_export | slow_log、explain、db_metrics、index_info、ddl(受控)、analyze |
| 默认绑定上下文 | 语义模型 | 数据集（表范围+语义模型） | 目标库 + 时间窗 |
| 产物卡 & 右栏 | SQL 卡 + 结果表 / 语义 YAML | 图表 + 结论 + 报告 / 数据集&报告 | 诊断报告 + 修复计划 / 根因&执行计划 |
| 审批策略 | 只读 auto；大扫描按预估成本 confirm | 以只读为主，auto-edit | DDL/ANALYZE 等破坏性 confirm/deny，生产强制确认 |
| 输出契约（完成标准） | 结果集 + 可复跑 SQL | 图文分析报告 | 诊断报告 + 可选修复动作 |

### 4.2 对话生命周期（四阶段）

1. **创建**：唯一对话入口是首页 composer。直接输入（自动路由识别场景）或点场景 Tab / 推荐问题（显式指定预设），都走"新建一个带预设的对话"；对话在首次发送时才真正创建（对应现有 `newDialogue` 时机）。**场景 Tab = 预设初始化器，不是入口。**
2. **运行**：对话携带预设（六维配置束）；头部 preset chip 显示当前场景+绑定物；左栏 timeline 记痕。
3. **切换**：会话中允许换预设 = 一次 timeline 事件（"场景切换：问数→运维"），重绑上下文、换工具白名单与审批策略，**历史不丢**。跨场景任务（"这数为什么不对？去查下"）在同一线程内完成。
4. **回看**：侧栏 ALL TASKS 按对话列，每条带场景着色标签、可按场景过滤；点进去以该对话最后的预设恢复。

> 用户视角：**一个入口、N 个预设、一条带标签的对话流**；不是三套并行对话系统。

### 4.3 取舍

- **不按场景硬拆三个对话入口**：跨场景任务会被强制切断上下文（真实任务常问数→分析→运维连环）；历史碎片化；且要求用户先选场景，与"自动路由"价值矛盾。
- **不走到完全无场景标签的极端**：默认正确性没归属（语义模型/数据集/目标库谁来绑？）；审批与审计无法按风险画像聚合。
- **取中间**：对话是一等公民，场景是对话的标签 + 初始化配置，且可切换。

### 4.4 实现映射（不新增对话系统）

- 对话 = `conv_uid`；场景预设像今天的 `chat_mode/scene` 一样存在对话上。
- 预设可放 `ext_info`，支持**按请求覆盖**（与 `harness_engine` 按请求覆盖同机制）。
- 切换 = 该轮 `ext_info` 写新预设 + 记一个 timeline 事件。
- 可选策略项：若合规要求生产运维严格隔离，可加"运维场景强制新会话"，**默认关闭**。

### 4.5 产品侧表现（对 IA 的修正）

- 产品导航**没有**常驻"三工作台"入口；mockup 顶部三个场景 Tab 仅为**设计预览切换器**。
- 场景体现为：对话头部**可切换的 preset chip** + 侧栏**场景着色标签 / 过滤**。
- 首页场景 Tab 保留为创建期的预设初始化器（可发现性 + 正确默认值）。

## 五、场景插件化（专家套件形态）

**命名对齐（2026-10-22）**：产品左栏模块名统一为**专家套件**（置于"扩展"分组，对齐 AntWork 侧栏）；可安装单元称**套件 / scenario suite**（`suite.yaml`，`kind: scenario-suite`，即六维预设束）；本文"场景插件"均指该单元，与"套件"同义，仅历史命名差异。管理页为 §7.7 专家套件管理页。

**核心思路**：把六维场景预设束（§4.1）打包成**可安装、可版本化、可分发**的单元——即"场景插件"，采用专家套件形态（Skills + MCP + 提示词 + 策略的角色/行业工具包，带版本号与技能数）。轴向差异：专家套件面向角色/行业，场景插件面向任务场景；机制同构。此后**首页完全插件驱动**：场景 Tab、推荐问题、自动路由关键词均由"已安装且启用"的插件渲染；产品核心只剩 engine + 插件运行时 + 市场。

### 5.1 六维预设 → manifest 映射

| 六维预设 | manifest 字段 | 说明 |
|---|---|---|
| 角色 & SOP | `sop:` (playbook md) | 注入 system prompt 的行事规程 |
| 工具白名单 | `tools.allow / deny / provide_mcp` | 引用内置工具或自带 MCP server |
| 默认绑定 | `context_defaults:` | semantic_model: required/optional、dataset、数据源范围 |
| 产物渲染 | `artifacts: [sql_card, result_table…]` | 引用**核心渲染器注册表**，不自带 UI 代码 |
| 审批策略 | `approval_overrides:` | 只能**加严**不能放宽（见 §5.4） |
| 推荐问题/路由 | `recommended_questions:` + `routing:` | 首页 Tab 与自动路由关键词由插件供给 |
| 编排策略 | `execution: react \| flow` | 自由 ReAct，或引用某条 AWEL flow 做锚定编排 |

### 5.2 manifest 示例（智能取数）

```yaml
kind: scenario-plugin
name: db-query
display: 智能取数
icon: 🔍
version: 1.0.0
scenario_id: query
execution: react
routing:
  keywords: [查, 统计, 导出, GMV, 客单价, top]
sop: prompts/query-playbook.md
tools:
  allow: [semantic_search, schema_link, nl2sql, sql_execute, export_csv]
  deny: [ddl, shell]
context_defaults:
  semantic_model: required
artifacts: [sql_card, result_table]
approval_overrides:
  - match: {tool: sql_execute, est_scan_gb: ">100"}
    action: confirm
    reason: 高代价扫描
recommended_questions:
  - {text: 查询上月各区域销售额, hint: 按 region 汇总，含环比}
output_contract: result_set+sql
```

### 5.3 收益

- **首页插件驱动、核心变薄**：三个内置场景作为**官方插件**出货（dogfood 运行时）。
- **企业可扩展**：客户自发布场景插件（如"供应链对账"），卡片形态对齐专家套件（图标/描述/N 技能/版本/安装+、企业专属 tab）。
- **可版本化可复现**：对话创建时 pin `db-query@1.0.0`，timeline 记插件版本；升级不破坏历史会话；审计可回答"这次结论是哪个插件版本跑出来的"。
- **与行业套件可组合**：行业专家套件 = 场景插件 + 领域语义模型 + 领域 skills + 领域知识（如"财报分析专家"= 智能分析插件 + 财报语义模型 + 年报解析 skill）。
- **对齐业界**：AntWork 专家套件、DataWorks 内置 Skills、DB-GPT 现有 SKILL.md+zip 均为同一原语的不同包装。

### 5.4 安全边界（什么不能插件化）

- **执行引擎留在核心**：审批 gate、沙箱、语义层存储是 enforcement 点；插件只**声明**策略规则，由核心 gate 统一执行。
- **策略只能加严**：插件 `approval_overrides` 可加 confirm/deny，**不能**把核心 deny 放宽成 auto（合并顺序：core deny > plugin > core default）。
- **UI schema 化**：插件声明产物卡类型+参数，渲染器由核心注册表提供，不允许插件带任意前端代码。
- **工具隔离**：插件自带工具一律走 MCP server（进程隔离）或沙箱内脚本，不允许 in-process 任意代码。
- **路由冲突**：多插件关键词重叠时按 specificity + 管理员排序决出；首页可显示"由哪个插件响应"。

### 5.5 与现有资产的关系

- **Skills**：skill = 会话内可调用过程；插件 = 会话级预设束，**可内含多个 skills**（套件含 N 技能）。复用 pi `_skill_tools` 与 SKILL.md+zip 上传通道。
- **AWEL flow**：可作为插件工具引用（如"报告生成 flow"挂为 analysis 插件的工具）。
- **approval.py**：核心 gate 不变，插件规则作为策略源之一并入（多源配置）。

### 5.6 产品侧表现与分期

- **专家套件管理页（新增模块 · 左栏"扩展"分组入口）**：卡片网格（图标/名称/描述/N 技能/版本/安装·启用），官方内置 / 企业专属 / 市场 分组；banner 引导行业套件创建（"让 DB-GPT 帮我创建"）。
- **分期**：P0 = manifest schema + 运行时，三内置场景重构为官方插件，首页/路由/预设从插件渲染，对话 pin 插件@版本；P1 = 专家套件管理页（安装/启用/升级/卸载、zip 上传、企业专属、推荐问题可编辑）；P2 = 市场发布、策略合并 UI 与按插件版本审计、"一句话生成场景插件"（meta-agent）。

### 5.7 对标新版 DataWorks Data Agent 的产品侧调整

参考新版 Data Agent（基于 Qwen Code 的全页面形态）做以下产品侧调整：

1. **实例化运行上下文**：工作台头部增加**实例 chip**（工作空间/数据源范围 + 资源配额 + 运行状态，如 `⚙️ 实例 ws-prod · 4CU · 运行中`），对齐 DataWorks 实例（工作空间+资源组+CU）。对话 pin 实例上下文；web 端部署默认常驻，**不照搬**其"1 小时不用自动停机"（该策略服务于其 CU 计费，我们无此计费形态）。
2. **确认机制补全为八类**：计划确认 / 破坏性操作 / 发布上线 / 信息补充 / 高代价操作 / 跨边界操作 / 权限变更 / 长任务中断。设计稿补**计划确认卡**（复杂任务拆解后先展示执行计划待确认）与**长任务进度卡**（关键节点告知进度，可继续/中断）；审批中心策略表补跨边界、权限变更两行。
3. **composer 底部对置 + `/` 显式调用**：模型切换与审批模式（五档命名对齐：plan 计划 / 请求批准 / auto-edit 自动编辑 / auto 智能审批 / yolo 完全访问）在输入框左下对置；新增 `/` 入口显式调用技能/插件；与意图自动路由形成**双轨**（场景路由 + 技能路由，对齐 `/dataworks-chatbi-skill` 显式指定与自动路由并存）。
4. **技能双轨与实例级开关**：官方内置 + 自定义上传（SKILL.md+zip，≤50MB）；启用/停用按**工作空间（实例）级**生效；分析类能力作为官方插件/技能可自动路由命中。
5. **全页面独立工作台保留**：对齐新版全页面形态（非侧边栏面板）；会话列表沿用全局侧栏 ALL TASKS（带场景标签+过滤），不另设工作台内会话列表，避免双份列表。

### 5.8 一个 agent + 三套件：套件 vs 核心边界

**结论**：三类场景的差异 = 三个专家套件的差异；**agent 只有一个**（一个 ReAct 运行时）。套件是配置，agent 是执行器。

**进套件的（声明式载荷，每场景一份）**：

| 维度 | 例 |
|---|---|
| SOP / playbook | 问数=schema-link→SQL→执行；分析=圈数据集→多步→图表→报告；运维=采集→聚合→根因→修复提案 |
| 工具白名单 + 自带 MCP | 问数无 ddl；运维有 ddl(gated)/slow_log |
| 默认绑定 | 语义层 / 数据集 / 目标库+时间窗 |
| 产物声明 | sql_card / result_table / chart / report / diag（引用核心渲染器） |
| 审批 overrides | 只能加严（高代价扫描 confirm 等） |
| 推荐问题 + 路由词 | 首页 Tab 与自动路由的数据源 |
| skills / few_shots | 套件内含 N 技能、样例 |
| 编排策略 | `execution: react \| flow`（自由 ReAct 或 AWEL flow 锚定） |

**留在核心（不进套件、不按场景分）**：ReAct 循环与 planner、审批 gate 的**执行**、语义层与 SemanticRetriever、渲染器注册表、会话/记忆、引用溯源、点赞自进化闭环、沙箱。原则：**套件只声明，核心来执行**。

**"一个 agent"的准确含义**：一个 agent 运行时 / 一个 agent 类；每个对话 = 被某个套件配置出来的一个 agent 实例（非单例同时服务所有会话）。套件切换 = 热加载配置 + 一条 timeline 事件，不新建引擎、不丢历史。

**唯一不能完全声明化的是控制流形态**：若某场景需固定管线（如报告生成走确定性后处理），靠 SOP prompt 拧 ReAct 拧不干净——故 manifest 以 `execution` 字段声明编排策略（react / flow），引擎照单执行；引擎仍是一个，差异仍落在套件。

**反向提醒**：不要为三场景建三个 agent——那会把记忆、评测、护栏、溯源各 fork 一份，套件化就白做了。

**收益**：核心薄到只剩 engine + 插件运行时 + 语义层 + gate + 渲染器；新场景 = 新套件，零引擎改动；评测按套件组织（推荐问题 + verified 样例即 eval set）；三个"工作台"纯为视图层差异（由套件声明的产物类型驱动）。

## 六、全局交互范式（三工作台共用）

沿用已落地范式，保证场景间一致：

1. **左栏 timeline**：意图行 → 分组工具行（连续同名工具合并）→ 产物卡；节点状态 done/running。
2. **中栏对话**：用户气泡（渐变）+ Agent 行（头像+文本+产物卡）。产物卡类型：SQL / 结果表 / 图表 / 报告 / 诊断。
3. **右栏查看器**：默认收起；点产物卡"展开"或头部 ⋯ 滑出；内容随场景（语义模型 YAML / 诊断详情 / 数据集表清单 / 报告）。
4. **审批 Dock**：悬浮 composer 上方；approval 与 question 叠放（approval 优先）；决议后消隐并回灌 observation。含：风险等级、影响面/预估成本、批准/拒绝/替代方案、记忆作用域（仅本次/本会话/始终询问）。
5. **Composer（工作台内）**：审批模式 chip（计划/请求批准/自动编辑/智能审批/完全访问）+ 语义模型或数据集 chip + 发送。
6. **全局状态线**：流尾一行，运行中圆点 + 工具数 + Token 输入/输出 + 耗时。
7. **头部 preset chip**：显示当前场景预设（按场景着色），点击可在四预设间切换；切换即重绑上下文、换工具白名单与审批策略，并写一条"场景切换"timeline 事件，历史不丢（见 §4）。

## 七、各页面设计要点

### 7.1 首页 Explore
- 保留现有：左侧栏、顶部标题栏、居中 hero（logo+标题+slogan）、大 composer（图标行+模型选择+麦克风+发送）、底部 pill。
- **改造点**：composer 下方原 "RECOMMENDED EXAMPLES" 平铺卡 → **场景 Tab 行 + 该场景推荐问题列表**。Tab 带图标+描述；推荐问题为可点击行（hover 高亮），点击填入 composer 并路由。
- **无常驻三工作台导航**：场景 Tab 仅是创建期预设初始化器，对话在首次发送时创建；进入后统一为同一对话外壳，场景体现为头部可切换 preset chip 与侧栏场景标签（见 §4.5）。
- composer 内新增：智能路由 chip（实时显示识别场景）、审批模式 chip、@上下文 chip。
- 首页不放重仪表盘；最近会话/概览信息收进侧栏 ALL TASKS 与对应模块页。

### 7.2 智能取数（DB 取数工作台）
- 头部常驻 **语义层 chip（紫）**：显示数据源 + 表白名单规模；右栏查看器展示命中语义条目的权威定义。
- **语义使用链（单发精准）**：① 问前置 `SemanticRetriever` 双路召回（向量 top-k 按 type 过滤 + 结构化精确匹配同义词/指标名）→ ② 按 `metadata.id` 回结构化库加载权威定义（公式/默认过滤/join 路径/规则；向量只是索引不是真相）→ ③ 组装 prompt（指标表达式+默认过滤+join+白名单）→ NL2SQL → ④ 执行层规则护栏落地（只读 SELECT、超时/行数、只读从库、行级权限）→ ⑤ 答案下**引用溯源** chips（指标 v2/表/样例/规则）→ ⑥ 👍 沉淀样例库、✏️ 纠错进语义标注待审队列。
- 对话流呈现：timeline 记"语义召回/加载权威定义/规则注入/引用溯源"步骤；SQL 卡注释标明默认过滤与规则注入来源；结果卡显示执行库（只读从库）与耗时。
- 高危/高代价操作弹审批 dock（如大扫描预估成本、DDL 变更）。

### 7.3 智能分析（DB 数据分析工作台）
- 头部常驻 **数据集 chip**（=语义层表白名单圈定的表范围）+ **语义层口径 chip**，可切换。
- **语义使用链（多步一致）**：① 数据集圈定 = 语义层**表白名单 + 血缘 join 路径**（模型不从全量表选表）→ ② 多步取数每步引用**同一指标定义（版本 pin）**，保证跨图/跨步口径一致 → ③ 默认过滤/时间粒度统一注入，各步无需重复口径 → ④ 报告结论**引用指标版本+样例+join**，读者可溯源 → ⑤ 报告 👍 沉淀样例、✏️ 纠错进待审。
- 与取数场景的差异：取数把语义层当"精准口径源"（单发 SQL+引用），分析把语义层当"多步一致性约束"（数据集圈定+口径统一）；二者共用引用溯源与点赞自进化闭环。
- 对话流：理解需求 → 圈定数据集 → 多步取数 → 图表卡（柱/线/饼自动匹配）→ 结论提炼卡 → 报告卡（HTML/PDF 分享，含引用 chips）。
- 右栏查看器：数据集表清单（白名单态）+ join 路径 + 报告预览。

### 7.4 智能运维（DB 运维工作台）
- 头部常驻 **目标库 chip + 时间窗 chip**。
- 对话流：意图 → 采集执行计划/慢日志 → 聚合多维信息 → 根因定位 → 诊断报告卡（慢查询表+修复建议）。
- 修复类操作（DDL/ANALYZE）弹审批 dock（破坏性/生产环境标识）。
- 右栏查看器：根因详情 / 执行计划 / 血缘影响。

### 7.5 语义层 · 知识中心（新增一级模块）

定位：**Agent 的语义记忆**（而非仅 BI 口径治理）——每次取数都记得业务口径，并越用越准。数据流：Datasources → ① 元数据目录（自动同步只读）→ ②~⑥ 语义知识层（LLM 草稿+人审 / 指标 / 血缘 / 样例 / 规则）→ 混合检索 → AWEL·NL2SQL Agent；对话点赞/纠错回流样例库与待审队列。

**产品定义**：
- 顶层对象 = **语义空间**（每个数据源连接一个，自动创建，命名 `semantic::<conn_id>`）；模块 = 治理面 + 服务面；空间内六 tab + 空间设置（embedding 模型 / 采样范围 / 重建索引 / 托管空间入口）。
- 空间状态机：**未激活**（L1 只读浏览）→ **已激活**（L2-L6 治理 + 检索消费）；瞬态 syncing / 漂移待审。
- 角色：浏览（含引用溯源）/ 标注（草稿编辑与审核）/ owner（发布、规则、白名单）/ 管理员（空间设置）。
- 消费面不止本模块：chat 引用 chip、套件 semantic 绑定（scope/pin/proposals）、KB 托管空间只读视图、P2 Semantic-as-API/MCP。

**Onboarding 模型：显示自动、治理显式**：
- Datasources 连接后语义空间**自动创建**、L1 元数据后台同步并显示（零配置、只读）——"连上即可用"的分级可用入口。
- **激活治理** = 一键确认三件事：采样范围（默认高频 top-N）、是否立即跑 LLM 草稿生成、embedding 模型（与空间绑定，换则全量重建）；其后草稿/挖掘/白名单/检索消费点亮。成本项（LLM token、embedding）opt-in。
- 语义中心**不独立管理连接**（连接唯一真源 = Datasources）；外部语义定义（yaml/csv）可导入，属内容非连接。
- 对标取舍：DataWorks 语义分析 = 重显式建任务（源+业务域+重点表+代码空间）；ChatBI = 显式建数据集；本设计取中间：**L1 自动登记 + 一键激活 + 空间内任务化**（草稿生成/指标挖掘为后台作业，非建空间前置表单）。

**实施状态（2026-10-23）**：
- 空间列表页已落：登记存量连接（backfill）、一键激活（采样/草稿/embedding）、覆盖率统计条；空间内六 tab + **生成草稿**按钮 + 标注置信度列（审核队列按置信度排序）。
- L2/L3/L4 生产者已落：标注器双模（LLM JSON / 启发式四档置信度：comment 0.95、键/时间/布尔 0.70、枚举 0.60、其余 0.50）、指标矿工（金额列 SUM + 每表 COUNT 候选 / LLM 提案）、join 发现（FK→active 免审、命名启发→draft 待人工校准）；LLM 桥经 `CFG.LLM_MODEL`+WorkerManager 解析服务默认模型，无模型在服时静默降级启发式。
- 消费侧（SemanticRetriever 双路召回 / sql_guard / 引用 chip / 点赞回写）= 阶段三，见 `semantic-center-impl-plan.md` §四/§九。

- **六 tab 治理面**：① 元数据目录（schema/comment 自动同步、只读、大库采样提示）② 语义标注（LLM 草稿+置信度→人审 确认发布/修改/驳回；**草稿不进入检索**）③ 指标口径（版本化可溯源：expression/表/维度/默认过滤/时间粒度/owner/状态）④ 样例库 Verified Q→SQL（点赞沉淀/人工导入、使用次数）⑤ 关系/血缘图谱（join 路径带 join key，供 schema linking 与可解释性）⑥ 规则护栏（只读模式/行级权限/默认软删除过滤/表白名单/超时行数/只读从库）。
- **存储分工**：指标/规则/血缘/枚举/版本/owner → 结构化库（**权威源**）；描述/同义词/样例检索文本 → KB 托管空间（**派生索引**；chunk=一条语义项，带指针 metadata{id,type,target,version}；托管空间在 KB UI 内只读防绕过治理；换 embedding 模型全量重建）。
- **发布管道**：编辑草稿（仅写结构化库）→ 人审发布（status=published, version+1）→ 写托管空间（按 metadata.id 删旧 chunk→插新→embed）。
- **混合检索**：向量 top-k（按 type 过滤）+ 结构化精确匹配（同义词/指标名）→ 按 id 加载权威定义 → 组装 prompt；AWEL 算子 `SemanticRetriever`。
- **消费面**：P1 平台内一级模块 + 托管 KB 空间 + Chat 引用溯源；P2 抽 Semantic Service（API/MCP，定义 YAML+git 版本）；P3 可选独立服务。对标 Snowflake（定义即一等对象）/ dbt（声明式+版本）/ ThoughtSpot·Cube（消费侧对 AI 开放），自补 Agent 语义记忆（检索+样例+自进化+溯源）。
- **冷启动**：复用现有 DBSummary 表摘要作为初始 chunk，再由语义层草稿+人审逐步增强。

### 7.6 审批中心（新增一级模块）
- 待办队列：待确认操作（工具/风险/发起人/会话/超时倒计时），批准/拒绝/改参数。
- 策略规则：auto/confirm/deny 规则表（属性声明→参数模式→上下文→LLM 意图解释），支持 UI 增改与试运行框。
- 白名单/记忆：once/session/always 作用域管理。
- 审计：历史决议流水。

### 7.7 专家套件管理页（新增模块 · 左栏"扩展"分组）

- **入口**：左栏"扩展"分组（左规尺缩进，对齐 AntWork 侧栏形态）→ **专家套件**；同组还有技能、连接器。页面 = 列表（搜索 / 添加 / 查看我发布的 / 已安装 N）+ 详情（slug / 版本徽标 / 来源徽标 / @作者 / README / 快捷命令 / manifest 关键值）。
- 形态对齐专家套件：卡片网格（图标 / 名称 / 描述 / N 技能 / 版本 / 安装·启用按钮）。
- 分组：官方内置（三场景官方插件）/ 企业专属（租户自发布）/ 市场；顶部 banner 引导行业套件创建（"让 DB-GPT 帮我创建"）。
- 卡片详情：manifest 预览（YAML）、内含 skills 列表、approval_overrides 明示（只读，标注"仅可加严"）、推荐问题编辑（P1）。
- 启用态联动：启用后首页出现对应场景 Tab 与推荐问题；停用即从首页移除（进行中对话保留 pin 版本直至结束）。
- 列表顶栏：搜索 + 添加（zip 上传）+ "查看我发布的套件"；"已安装 N" 统计跨组已启用套件（对齐专家套件列表页）。
- 套件详情页：返回列表、slug + 版本徽标 + 来源徽标（官方内置/企业套件）+ @作者 + 安装按钮；README 描述；**快捷命令（/command 列表，会话内可调用）**；manifest 关键值（execution / tools.allow / approval_overrides 仅可加严 / context_defaults）。
- 首页套件激活形态：选中套件/场景后 composer 内注入**套件前缀 chip + 场景提示**（对齐专家套件首页形态）；推荐问题支持"换一批"轮换。

## 十、开放问题

1. 场景 Tab 是否要支持用户自定义（增删场景+推荐问题）？倾向 P2 做，进 setting 界面。
2. "技能与 Agent" 作为首页 Tab 还是仅侧栏入口？当前放 Tab 以对齐现有 "Create SQL Analysis Skill" 示例的心智。
3. 语义模型与知识库的边界展示：语义层=权威源、KB=派生索引，是否在语义层详情页显式标注来源 chunk 指针？倾向是。
4. 插件与专家套件的边界：倾向场景插件为基础原语，行业套件为组合包（内含场景插件+领域语义模型/技能/知识），二者共用同一运行时与市场卡片形态；是否在 P1 即支持组合包，还是 P2 再做？
