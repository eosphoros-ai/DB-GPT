# 财报专题并发生成与并行校验

在布局恢复、工具路由和精简上下文的未提交修改基础上继续实现。没有提交 Git，没有重启日常服务。测试配置、数据库、文件、模型会话和日志复用 `.work/financial-analysis/speed-layout/` 的独立作用域。

## 运行方式与一致性

`prepare_financial_report` 提取一次 PDF 后，默认最多三个专题同时生成。每个任务使用同一批次的独立快照，完整执行现有字段、数字、事实/计算引用、证据与专题覆盖校验；校验通过 `asyncio.to_thread` 在工作线程执行，不占用报告写锁。每个专题最多三次生成/修复，模型等待使用累计 120 秒预算。修复保留其他有效草稿字段。

同一服务进程的所有报告最多六个生成/校验任务。没有同时写共用 revision：协调器持有短锁检查 owner/session、批次标识、批次状态和待提交专题，只合并该专题的已校验结果，再生成新 revision。字段校验不在锁内重复执行。专题结果按固定顺序排序，完成先后不影响展示顺序。模型没有提交这个内部结果对象的 API。

批次执行期间，显式专题修改和复核被拒绝，报告事实与计算不会变化。因此在该批次快照上校验的结论可安全合并。重复结果、已取消批次和重启前的迟到结果不能提交。取消只保留已经合并的专题；仍在工作的校验线程只接触私有副本，无法在取消后写报告。服务重启将批次标为 interrupted，并允许恢复尚未完成专题。

合并后仍由主智能体拿完整复核上下文，显式逐项复核；revise 继续修订，完整复核后才自动发布。模型超时或失败由后端错误码记录，不解释成数据缺失。部分发布、单专题重做、历史、来源和导出继续使用已有流程。已有报告不会因为再次 prepare 而重新批量生成。

章节 `section` 是专题的确定性路由，由后端填入；不会因为模型填错章节消耗修复轮次。财务数值和引用仍完整校验。费用覆盖清单由实际可用科目生成；期间引用来自实际数据，没有针对公司、文件名或特定年份的分支。

当前版上传至最终回答约 **2 分 50 秒**，比上一阶段 277.2 秒缩短约 38.8%；根运行缩短约 40.3%。但本轮**只有三个专题通过**：经营表现、现金流、资产负债。扣非专题因无依据原因判断失败，毛利因重复单位失败，费用因未覆盖研发费用失败。它们均到达已有的三次失败上限，没有放宽校验、删除错误后假装完成或将错误改为缺数据。因此不能宣称“同等覆盖下已达到 2～3 分钟”，当前完整通过率是明确的剩余问题。

当前版校验累计墙钟计时 **126 毫秒**，含线程调度；并发批次约 108 秒。校验已经在线程间重叠执行，但它不是主要耗时。实测收益来自模型请求并发及上下文缩小，不应宣称校验自身带来几十秒收益。修复较多使总模型调用从 11 增至 18，输出字符也增加，不能将主智能体仅三轮写成全部模型仅三次。

输入统计将主智能体序列化消息字符与专题 system/context 内容字符相加，封装口径略有差别，只作为近似体量比较；没有可用 token 统计。批次保留每专题调用、输入输出字符、耗时与校验时间，不保存提供商异常内容。

## 后续：三个失败专题的局部修复

进一步查看真实失败草稿后，不能将三项都概括为格式问题：

- 扣非草稿里的“是否源于主业、尚待验证”已经是核查问题，但放在 summary；新增定位反馈要求将它移至 unresolvedQuestions，保留摘要里有依据的观察和原问题，不通过增加模糊免责声明放行。
- 毛利草稿不只是占位符后重复了“元”，还把本期营业成本金额写成减少额。新增 `fact_level_used_as_change` 校验，与重复单位错误在同一轮返回。删除单位后，错误的增减额表述仍被拒绝；应写本期/上期金额比较或引用已有的变化计算，不能自行算差额。
- 费用草稿漏掉研发费用。新增 `append_findings`，只补缺失科目，允许与 patches 合用，保留其他草稿。错误反馈给出缺失科目的真实事实与引用；合并后完整校验。费用覆盖要求摘要实际使用相关事实/计算，不能只挂一个未使用的 ID。

对应修改在 analysis.py、workflow.py、parallel.py、financial_tools.py、财报 Skill 和三个测试文件。并发模型调用方式、三次失败上限和显式复核保持不变。

针对性完整套件 **140 项通过**（新增五项），包括单字段多错误、单位修正后仍拒绝错误增减额、问题迁移、两种不同缺失费用的追加修复、非法追加仍拒绝、工具入口与并发修复链路。初次新增测试遗漏 analysis fixture 导致两个失败，补齐测试数据后通过；没有调整生产逻辑来迁就测试。

读取独立测试库中的原三个失败草稿，在内存副本上复现错误并应用人工构造的局部修正，三项均转为 ready，事实及其他专题发现不变。证据为 `.work/financial-analysis/speed-layout/repair-replay.json`。这是校验器回放，不是模型生成验收；没有修改已发布报告或日常数据库，也没有新的模型耗时/稳定通过率结论。上表保留改造前的实测，不能当作这些新反馈的性能结果。

## 使用

重启后端后，新建聊天上传财报即可；无需迁移数据库或重建前端。可在启动后端的 PowerShell 设置单报告并发数，默认 3，限制为 1～6：

```powershell
$env:DBGPT_FINANCIAL_CONCURRENCY='3'
uv run --env-file .env --no-sync dbgpt start webserver --config configs/dbgpt-proxy-tongyi.toml
```

提供商允许的并发、吞吐限制和每条发现的生成时间会影响实际速度。当前设计沿用单进程服务的写锁，不支持多个后端进程同时协调同一数据库报告。并行线程消除了事件循环与写锁里的校验等待，但 Python GIL 使纯 Python CPU 工作不等同于多核加速；实际主要收益来自模型请求重叠和缩小每个请求上下文。
