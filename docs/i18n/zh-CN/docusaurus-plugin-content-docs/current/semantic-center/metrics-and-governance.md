# 指标与治理

指标定义是一份计算约定。它应足够明确，让另一位使用者能够复现。

| 选择 | 需要确认的问题 |
| --- | --- |
| 公式与单位 | 毛额还是净额？是否含运费？元还是万元？ |
| 粒度 | 按订单、支付、退款、客户还是日期计算？ |
| 有效性 | 哪个租户、状态、真实或测试订单？ |
| 时间 | 下单、支付还是退款时间？时区与区间边界是什么？ |
| 关联与去重 | 多条商品、支付、退款记录是否互相放大？ |
| 依赖 | 使用哪些字段、维度和基础指标？ |
| 依据 | 谁确认定义，当前使用哪个版本？ |

上述属性只有保存到定义中才可使用，工具不会自动补造缺失过滤和时间字段。

## 草稿与发布版本

草稿是待审核提议。当前界面支持检查与发布，自定义指标准备和修改需通过[上手指南](./quickstart.md)
说明的维护流程完成。发布保存快照；指标搜索和读取返回已发布快照，不回退草稿。多步分析应复用返回的整数版本。

如果要求版本 2 而该版本不存在，应先处理缺失定义，不能默默改用最新版本。

## 模拟案例：收支时间与关联粒度

电商演示中，订单可能 12 月下单、1 月付款、2 月退款。GMV 与净实收对 1 月的结果可能合理不同，取决于已发布的时间归属约定。

两条商品、两条支付和两条退款直接 JOIN 可能产生八行。应先按目标粒度聚合事件来源再组合，并按定义验证，而不是记住一种固定 SQL。

## 修改口径

审核变化和依赖影响，发布新版本，重跑代表性问题并对比旧版本结果。报告保留版本引用。当前工具不自动跨会话 pin 版本，也不证明所有下游 SQL 完整遵循口径。
