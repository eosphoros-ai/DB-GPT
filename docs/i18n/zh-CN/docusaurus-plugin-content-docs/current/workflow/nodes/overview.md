# 节点类型与编排契约

工作流 DAG 由少量节点类型构成：智能在 `agent` 节点里，其余是边界、数据面与门。

## 类型参考

| Kind | 角色 | 说明 |
|---|---|---|
| `start` | 边界 | 入口；把用户原问广播给所有节点 |
| `output` | 边界 | 唯一 DAG 叶子；最后一个节点的产出成为整轮最终答案 |
| `agent` | 智能 | 隔离的 ReAct Agent：目标 + 工具边界 + 输出契约。主力节点，见 [agent 节点](./agent.md) |
| `file_data` | 数据面 | 确定性 CSV/Excel 加载：上传解析、行数上限、摘要。刻意保留为算子——解析与截断保护放算子层比放 Agent 稳 |
| `human_confirm` | 门 | 暂停运行，在输入框上方浮确认 dock；批准继续、拒绝/超时失败。见[确认门](./human-confirm.md) |

### 已退役类型

早期世代的硬算子类型已退出面板与内置模板；存量 flow 仍可编译兼容，但新工作请用 agent：

| 退役 kind | 替代 |
|---|---|
| `db_query` | 带 `sql_query` 工具的 `agent` 节点（接地契约取代盲提取） |
| `ai_analysis` | 带分析目标的 `agent` 节点 |
| `visualize` | 图表进入报告节点的 HTML 产物 |
| `report`（硬算子） | 带报告契约的 `agent` 节点（仅 `html_interpreter`） |

## 数据通道

每个节点的 user message 按执行顺序包含：

```
<config 里的 goal>

用户问题: <终端用户原始消息>

上游节点产出(按执行顺序):
<source node="模式与语义接地" kind="agent">
…该节点的干净最终产出…
</source>
<source node="透视分析" kind="agent">
…
</source>
```

两个值得内化的推论：

1. **所有在前节点的产出，而不只是父节点的。** 三跳之后的复核节点仍看得见接地卡。总上下文
   有预算（约 2 万字符），超了先截最老的块；
2. **产出即契约。** UI 协议（步骤 marker、产物 fence）在喂给下一个 Agent 前会被 strip——
   向后流的正是该节点回答的内容本身。

## 写输出契约

每个 goal 以一行显式 `输出:` 收尾，点明交付物形态，例如：

> `输出:语义卡(表/字段/口径/方言)+数据量概览。`

下游 goal 则写"基于上游语义卡……"——契约就是接口。没有契约的节点倾向于用散文回答，下游
只能猜。

## 控制与数据

边定义**控制顺序**（节点何时可以启动），不限制节点**看见什么**——那是数据通道的事。星型
DAG（所有边从 `start` 直发）同样能让每个节点收齐上游上下文；深链主要买到的是顺序与可读的
运行卡。
