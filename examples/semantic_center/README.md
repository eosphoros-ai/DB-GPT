# 语义中心案例：电商收支与元数据

这是一份可复现的模拟业务案例，用于验证智能取数和元数据场景如何消费业务语义、
指标口径与血缘证据。所有交易、商品、渠道均为虚构数据。
案例生成器使用项目真实的 SQLiteConnector、SemanticSyncService、
SemanticService、SemanticReader 和四个 semantic 工具，隔离于运行服务的元数据库。
模型输出质量和在线向量检索不在离线验证范围内。

## 生成与验证

在仓库根目录运行（依赖项目开发环境）：

```bash
.venv/bin/python examples/semantic_center/build_case.py \
  --output output/semantic-center-case-20261028
```

输出目录必须不存在，避免覆盖已有案例。重复验证请换新目录。
生成 `commerce.db`（业务库）、`semantic_meta.db`（隔离治理库）、
`semantic_seed.json`（按表字段命名的导入定义）、
`cases.json`（12个问题与预期）、`expected.json`（独立硬编码金标）、
九份 SQL、`schema.sql`、`data_dictionary.csv`、`view_lineage.sql`、
`relationships.mmd`（真实外键ER图）、
`governance.json`、`tool_evidence.json` 和 `verification.md/json`。
脚本通过审核发布路径创建定义，发布索引使用 LoggingSink。
**不要将 semantic_meta.db 替换服务现有元数据库。**

## 数据与口径

6张实体表：channels、products、orders、order_items、payments、refunds。
1个实际 SQL 视图：v_cash_events。表结构包含5条声明外键。
订单10笔、商品明细11条、支付11笔、退款6笔，便于逐笔核算。

固定窗口为 `[2026-01-01, 2026-02-01)`，时间采用 UTC+08；金额存储为人民币分，
展示时除100。有效订单限定租户1、非测试、非软删除、状态PAID/COMPLETED。
失败支付/退款不计入；当前订单状态用于本固定快照，不支持任意历史时点状态重建。

| 指标 | 归属时间 | 运费与退款 | 1月预期 |
|---|---|---|---:|
| 净实收 v1 | 支付月减退款月 | 含运费，减成功退款 | 368.00元 |
| 净实收 v2 | 支付月减退款月 | 扣订单运费一次，退款仅扣货款 | 338.00元 |
| 有效GMV | 下单月 | 商品明细行总额，不含运费，不扣退款 | 400.00元 |
| 自然渠道净实收 v2 | 收支事件月 | 同v2 | 126.00元 |
| 广告渠道净实收 v2 | 收支事件月 | 同v2 | 212.00元 |

1月成功支付合计413.00元、成功退款45.00元，v1=368.00元。
1月支付订单运费33.00元、退款中的运费3.00元，
v2=413-33-(45-3)=338.00元。
v2运费扣除仅适用于本案例的完整结清订单；分月分期支付需要另行定义分摊政策。
`order_items.goods_cents` 是行总额，已经包含数量，不能再乘quantity。

订单1有2条商品、2笔1月支付、2笔1月退款。正确v1净实收为95元，
直接关联三个明细汇总得到380元（4倍）；`bad_join.sql`保留此反例。
订单3于12月下单、1月收款和退款；订单4于1月下单、2月收款。
订单1另有2月退款，不应扣入1月。测试订单、另一租户、软删除、取消、
失败流水各有明确反例。

## 在UI演示

1. 在数据源中新建 **SQLite**，连接名称必须为 `Semantic_Commerce_Case`，
   路径选择生成的 `commerce.db` 绝对路径。服务须能访问此文件。
2. 在语义中心找到该空间，记下空间ID。保持空间无已有标注、指标、样例，
   不要先运行AI草稿生成；只导入这个新建案例空间。
3. 在仓库根目录执行：

```bash
.venv/bin/python examples/semantic_center/import_case.py \
  --base-url http://127.0.0.1:5670 --space-id 这里替换为空间ID \
  --report output/semantic-center-case-20261028/live-import.json
```

脚本通过管理API同步、激活、创建标注并审核发布，再创建发布指标。
连接名不符或存在已有标注/指标/样例时拒绝导入；部分失败时报告保留已创建ID，
重复运行不会静默重复写入。服务器认证如有额外配置，需使用相应已授权环境。
脚本不会连接或修改主服务元数据库文件。

**线上版本区别：**现有REST没有指标编辑接口，所以首次导入
“净实收”（业务口径v2）发布版本为1；
“净实收_含运费对照”（业务口径v1）也发布为1。
这两个指标用于现场对照，不能声称是同一指标的历史版本。
同一指标真正的v1→v2、版本不存在不回退、未发布修改不泄漏，
已在隔离库走真实发布服务验证。

4. 智能取数选择该数据库，优先问：
   “按到账日期统计2026年1月净实收，只看租户1真实业务，先读取已发布口径。”
   预期338元，线上引用实际发布版本1。
   再问“按来源拆分”，预期自然126元、广告212元。
   版本对照现场问“净实收与净实收_含运费对照差多少”，预期30元。
5. 元数据与架构场景选择该数据库，问字段含义、ER关系、净实收字段来源、
   视图加工逻辑。ETL调度任务/负责人问题应明确无证据。
   其余问题见 `cases.json` 或 `verification.md`；其中Q03的真正同指标v1/v2
   与Q01/Q02显式@v2要求适用于隔离测试，UI需按上述实际发布版本调整。

每次检查工具记录：先检索业务词和指标，再读取具体发布口径；生成SQL和报告
应引用指标ID/发布版本，并说明金额单位、时间字段、过滤与粒度。
离线脚本不替代这一步真实模型验收；本交付未声称两个引擎已端到端通过。

## 针对性验收

| 类别 | 核心问题 | 应观察到的行为 |
|---|---|---|
| 业务语义 | 到账金额、货款、退钱金额、来源分别是什么 | 命中已发布同义词及具体字段，排除错误草稿 |
| 指标口径 | 净实收与GMV为何不同 | 区分时间、运费、退款、粒度；不能只按表名猜 |
| 版本 | 固定v1、获取最新v2、请求v99 | 正确读取不可变快照；未知版本不回退 |
| JOIN风险 | 商品/支付/退款直接JOIN | 解释扇出；先按订单汇总，避免95元变380元 |
| 元数据 | 字典、PK/FK、ER关系 | 读取实际结构与5条声明外键，说明一对多 |
| 指标依赖 | 退运费变更影响 | 依据已登记依赖影响v2，不影响v1和GMV |
| 加工来源 | v_cash_events如何产生 | 查看实际CREATE VIEW，支付/退款UNION ALL，仅支持v1 |
| 证据缺失 | 上游任务、负责人、运行时间 | 明确无调度证据，不能从FK推断ETL |

## 血缘边界与后续优化入口

- **表关联**：真实FK，已由JoinDiscoverer进入L4关系表，可从relations管理API读取。
  当前没有专用关系Agent工具；同步的列is_fk标志也没有完整反映实际外键，
  本案例不把标志视为外键真相，使用声明DDL和实际关系证据。
- **指标依赖**：在发布指标的metric_definition.lineage中手工登记字段、粒度，
  可随semantic_get_metric消费；这不是自动解析的列级影响图。
- **SQL视图加工来源**：SQLite实际保存的CREATE VIEW是证据，
  `view_lineage.sql`可追溯；v_cash_events不能直接算剔除运费的v2。
- **ETL任务血缘**：本案例没有调度平台，不提供虚构任务节点。

后续可用这12题作为回归集补齐关系/血缘读取工具、视图依赖解析、
指标依赖校验与反向影响查询，再在DBGPT和PI引擎下执行真实对话验收。
查询权限、租户过滤和资源护栏仍需执行层校验；
离线金标SQL的过滤条件不代表平台已经自动强制执行。
